緩存與存儲（Redis/R2）

學會把圖片、檔案丟進 R2，用 Redis 加速讀取，讓 AI Agent 知道什麼資料該放哪裡

4 緩存與存儲在 Vibe Coding 中的角色

在 Vibe Coding 的工作流中，緩存（Cache）與對象存儲（Object Storage）是讓 AI Agent 產生的應用從「能跑」變成「跑得夠快、夠穩定」的兩個關鍵概念。之前的課程已經帶你認識了 Supabase（PostgreSQL、Auth、Storage），但資料庫適合存結構化資料——使用者、訂單、設定——不適合存大檔案。當你讓 Agent 把使用者頭像、文章內嵌圖檔、上載的 PDF 全部塞進 Postgres 的 bytea 欄位或 JSON 欄位時，資料庫會因為每一次查詢都要搬運這些龐大 blob 而逐漸變慢，連線池也會被耗盡，這就是典型的 vibe broken 情境：API 回應時間從 50ms 飆到 5s，前端直接卡死。 對象存儲（如 Cloudflare R2）解決的是「檔案本身該放哪裡」的問題：圖片、影片、備份檔這些非結構化資料，不該存在關係式資料庫裡，它們應該被丟進 R2 取得一個公開 URL，然後只把 URL 存回資料庫。而緩存（如 Redis）解決的是「同一筆查詢重複執行很浪費」的問題：頻繁但資料變更不多的讀取（例如热门文章列表、API rate limit 计数、Agent 的短期會話快取）可以用 Redis 來卸載資料庫。AI Agent 在設計 tool 時，應該主動根據資料型別與讀寫頻率來選擇合適的存儲層，這是 Vibe Coding 從「原型」走向「可用產品」的分水嶺。

5 R2 存圖片 vs. 資料庫存圖片

以下這段程式碼展示了一種常見但錯誤的做法與正確做法的對比：讓 AI Agent 在 design tool 時犯下的典型錯誤。

❌ 錯誤：把圖片存進 Postgres
// schema.sql ALTER TABLE posts ADD COLUMN cover_image bytea; // Next.js API route import { put } from '@vercel/blob'; // 錯誤做法：把 base64 或直接 bytea 存進 DB await db.sql\`INSERT INTO posts (title, cover_image) VALUES (\${title}, \${imageBuffer})\`; // 讀取時 const row = await db.sql\`SELECT cover_image FROM posts WHERE id = \${id}\`; // 整個圖片 blob 都會被載入記憶體，查詢越頻繁 DB 負載越高
✅ 正確：圖片放 R2，DB 只存 URL
// 上傳到 R2（透過 Cloudflare R2 + Vercel 或原生 SDK） const { default: R2 } = await import('@cloudflare/workers-sdk'); const result = await r2.put(\`posts/\${id}/cover.jpg\`, imageBuffer, { contentType: 'image/jpeg', }); const imageUrl = \`https://cdn.example.com/\${result.key}\`; // DB 只存 URL await db.sql\`INSERT INTO posts (title, cover_image_url) VALUES (\${title}, \${imageUrl})\`; // 讀取時只拉一個字串 const row = await db.sql\`SELECT cover_image_url FROM posts WHERE id = \${id}\`; // 資料庫負擔大幅降低，CDN 負責加速圖片分發
3 上傳圖片到 Cloudflare R2 並取得訪問連結

這是最實用的實戰練習。假設你正在用 Cursor 或 Claude Code 幫你寫一個「圖片上傳」功能，正確的 workflow 是：前端選取檔案 → 前端直接multipart upload 到 R2（或用 presigned URL）→ 拿到 public URL → 存回資料庫。以下是 Agent 應該幫你產生的程式碼範例，使用 @cloudflare/workers-sdk 在 Vercel Edge Function 或 Cloudflare Worker 中執行：

# 1. 在專案中安裝 Cloudflare Workers SDK $ npm install @cloudflare/workers-sdk # 2. 建立環境變數（.env.local） # R2_ACCOUNT_ID=你的Cloudflare帳號ID # R2_ACCESS_KEY_ID=你的R2 Access Key # R2_SECRET_ACCESS_KEY=你的R2 Secret Key # R2_BUCKET=你的bucket名稱 # 3. 建立上傳 endpoint（app/api/upload/route.ts） $ echo "建立 app/api/upload/route.ts" # 實際執行時的預期行為： # 前端 POST /api/upload 送 multipart/form-data # 後端收到檔案後 put 到 R2 # 回傳 { url: "https://你的bucket.r2.dev/路徑/檔案名" } # 如果 R2 連線失敗，會回傳 500 與錯誤訊息 # 如果檔案超過 R2 單檔限制（10GB），會報錯 # 如果權限不足（Access Key 有問題），會收到 403
🔬 深入解析：為什麼圖片不能放資料庫？
當資料庫開始搬圖片，你的應用就在為不該它負的責任付出效能代價——這裡面到底發生了什麼？

關係式資料庫（PostgreSQL、MySQL）的設計哲學是「每次查詢都盡可能快，且資料要有結構」。當你把圖片（即使是 200KB 的壓縮 JPEG）存進 bytea 或 BLOB 欄位時，每一次 SELECT 這個資料列，資料庫都要把這 200KB 從磁碟讀進記憶體，再透過 TCP 傳回給你的 Node.js 程式。更糟的是，PostgreSQL 的 WAL（Write-Ahead Log）也會記錄這些資料的變更，意味著寫入圖片也會拖慢整個資料庫的寫入效能。 另外，資料庫的連線池（connection pool）是有上限的（通常 20-100 個連線）。如果每一次請求都要從 DB 讀取圖片 blob，連線很快就被耗盡，新來的請求就會排隊等待，這就是為什麼你的 API 回應時間會從 50ms 突然跳到 5s 的原因——不是程式寫錯了，是存儲層選錯了。 R2（以及 S3、Cloudinary 等對象存儲）的設計完全不同：它專為大檔案、低頻繁讀取、CDN 加速而設計。你上傳一次後，R2 會在雲端分散式儲存多個備份，並透過 CDN edge location 分發。資料庫只需要存一個 varchar(255) 的 URL，查詢時間穩定在 1-5ms，跟圖片多大完全無關。這就是為什麼 Vibe Coding 中的 Agent 在設計 schema 時，必須學會區分「結構化資料」與「非結構化資源」——放錯地方，vibe 就會慢慢 broken。

✏️ 小測驗

請先回答，再點擊「查看答案」

1. 以下關於 R2 與 Postgres 分工的描述，哪一個是正確的？
  • Postgres 可以存圖片，只要把圖片轉成 base64 字串放進 TEXT 欄位就好，這樣查詢速度更快
  • R2 是用來存結構化資料（如使用者資料、訂單），Postgres 適合存圖片、影片等大檔案
  • R2 適合存圖片、影片等非結構化大檔案，Postgres 適合存結構化資料；兩者各有專長，應搭配使用
✅ A 錯在 base64 會讓資料量增加約 33%，且 TEXT 欄位查詢時仍然要把整個字串搬進記憶體，並沒有比較快；B 錯在把兩者角色顛倒了——R2 專為非結構化大檔案設計，Postgres 專為結構化資料設計。C 正確說明了兩者的分工：R2 存檔案取得 URL，Postgres 存 URL 與其他結構化欄位，這才是 Vibe Coding 中 Agent 應該學會的架構決策。
2. 當你的 Next.js 應用突然變慢，資料庫 CPU 使用率飆高，但查詢邏輯沒有改變，最可能的原因是？
  • 你的 Postgres 版本太舊，需要升級到最新版本
  • 資料庫中可能塞入了大量非結構化資料（如圖片 blob），導致每次查詢都需要搬運不必要的大區塊
  • Next.js 的 React Server Components 與資料庫沒有直接關係，不會影響查詢效能
✅ A 是干擾項——Postgres 版本升級通常不會突然解決效能問題，除非有已知 bug，但這不是最常见的原因。C 描述的是正確事實（RSC 與 DB 效能無關），但它沒有回答「為什麼突然變慢」的問題。B 是最可能的原因：當資料庫中塞入了圖片 blob，每一次 SELECT 都要讀取、傳輸這些大資料，CPU 與 I/O 負載會急遽上升，這正是 vibe broken 的典型症狀之一，解決方案是把這些資料移到 R2，DB 只存 URL。
