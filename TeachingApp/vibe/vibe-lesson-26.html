Phase 5: The Money

支付系統（Stripe）

掌握非同步 Webhook 與結帳流程，讓 AI Agent 安全處理金流

1 Stripe 在 Vibe Coding 變現路線中的角色

在獨立開發者以訂閱制或一次性付費變現的產品中，支付系統是將使用者參與轉化為收入的核心基礎設施。Stripe 提供了一套完整的 API 與工具鏈，讓開發者能處理一次性付款、訂閱制、發票與退款，同時內建合規與安全檢查。在 Vibe Coding 的 AI Agent 工作流中，支付模組通常以「工具」形式被調用：AI 生成建立 Checkout Session 的程式碼、設定 Webhook 端點來處理付款成功或訂閱更新，並把狀態同步到資料庫（如 Supabase）。若你熟悉之前課程的 AI 協作模式，這裡的 Stripe 整合就類似於「工具設計與 Function Calling」章節：你把支付邏輯封裝成一個可被 Agent 呼叫的函式或 API 路由，讓 Agent 能根據使用者意圖自動觸發。當 Vibe 破裂（例如訂單狀態不一致、Webhook 未觸發）時，診斷步驟往往指向三個地方：API 金鑰是否正確、Webhook 端點是否公開可達、簽名驗證邏輯是否完整。記住，支付相關錯誤通常會在 Stripe Dashboard 的「Logs」與「Webhooks」頁面留下明確線索。

2 AI Agent 如何調用 Stripe Checkout 與 Webhook

AI Agent（如 Claude Code、Cursor 或自訂的 Coding Agent）在整合 Stripe 時，通常會分兩階段操作：第一階段生成「建立 Checkout Session」的前後端程式碼，第二階段生成「處理 Webhook 事件」的伺服器端邏輯。Stripe Checkout 是官方提供的-hosted 結帳頁面，使用者點擊後被導向 Stripe 的安全付款流程，付款完成後 Stripe 會透過 HTTP POST 發送事件到你的 Webhook 端點。Agent 在生成這段程式碼時，會呼叫 Stripe Node.js SDK（或 Python、Go 等官方套件），設定 product_id、price_id、success_url、cancel_url，並特別標記 metadata 欄位以便後續關聯使用者與訂單。Webhook 端點則是一個公開的 API 路由（例如 Next.js 的 /api/webhooks/stripe），負責接收事件、驗證簽名、並根據事件類型（如 checkout.session.completed、invoice.paid）更新資料庫中的訂閱狀態。若 Agent 忽略簽名驗證，攻擊者可能偽造 Webhook 請求；若忽略非同步特性，可能誤以為付款立即完成。因此，Agent 生成的程式碼必須包含重試邏輯與狀態檢查，而不是假設一次請求就能成功。

3 實戰任務：在測試模式下完成一筆虛擬訂單

本節任務目標是讓你在本地環境中完整走訪一次 Stripe 測試模式的結帳流程，理解非同步通知的實際行為。請先安裝 Stripe CLI 並登入，接著在 Stripe Dashboard 的測試模式下建立一個測試產品與測試價格，記錄 price_id。然後讓 AI Agent 生成一個 Next.js API 路由（/api/checkout），該路由使用 Stripe SDK 建立 Checkout Session，回傳 sessionId 給前端。前端使用 stripe.redirectToCheckout 進行跳轉。完成後，開啟 Stripe CLI 監聽 Webhook 事件，並在測試模式下完成一筆付款（使用測試卡號 4242 4242 4242 4242）。觀察終端機中收到的 checkout.session.completed 事件，確認你的伺服器是否正確處理了該事件並更新資料庫。這套流程能幫助你區分「同步的 HTTP 回應」與「非同步的 Webhook 通知」，並熟悉測試模式下的常见錯誤（如 price_id 錯誤、Webhook 端點未公開）。

🔬 深入解析：非同步 Webhook 的本質與容錯設計
為什麼 Stripe 要透過 Webhook 而非輪詢來傳遞付款狀態？

Webhook 的本質是「事件驅動架構」中的一種推送機制：Stripe 在發生特定事件（如付款成功、訂閱更新、退款）時，主動發送 HTTP POST 請求到你的端點，而不是由你的伺服器定期詢問 Stripe 的狀態。這種設計有幾個關鍵優勢。第一，即時性：付款完成後幾秒內 Webhook 就會觸發，適合需要即時啟用功能的訂閱服務。第二，效率：輪詢會產生大量無謂的 HTTP 請求，而 Webhook 只在事件發生時才通訊，減輕伺服器負擔。第三，可靠性：Stripe 會在失敗時重試（最多 3 次，指數退避），並提供事件 ID 供你檢查重複或遺漏。然而，非同步特性也帶來挑戰：你的伺服器可能因為重啟、網路問題或資料庫鎖定而無法即時處理 Webhook，導致狀態不一致。因此，可靠的設計需要包含「最終一致性」思維：接受短期狀態落後，但透過定期同步（如每日對帳）或 Webhook 重試機制確保最終正確。同時，簽名驗證不可省略，因為未經驗證的 Webhook 可能包含惡意數據，直接更新資料庫會造成安全漏洞。

⚖️ 情境對照：同步 API 呼叫 vs 非同步 Webhook

在支付流程中，開發者常混淆「同步的 HTTP 請求」與「非同步的 Webhook 通知」，以下對照兩者差異與適用時機。

同步 API 呼叫（建立 Checkout Session）
// 前端呼叫後端 API，立即取得 sessionId const { sessionId } = await fetch('/api/checkout', { method: 'POST', body: JSON.stringify({ priceId }), }).then(r => r.json()); // 接著導向 Stripe 結帳頁面 stripe.redirectToCheckout({ sessionId });
非同步 Webhook 通知（付款完成後）
// 伺服器端路徑，接收 Stripe 推送的事件 export async function POST(request) { const sig = request.headers.get('stripe-signature'); let event; try { event = stripe.webhooks.constructEvent(body, sig, endpointSecret); } catch (err) { return new Response('Webhook Error', { status: 400 }); } // 根據事件類型更新資料庫 if (event.type === 'checkout.session.completed') { const session = event.data.object; await updateSubscriptionInDb(session.metadata.userId, 'active'); } return new Response('Webhook received'); }
✏️ 小測驗

請先回答，再點擊「查看答案」

1. 在 Stripe 測試模式下，下列哪個測試卡號可用來模擬成功的信用卡付款？
  • 4000 0000 0000 0002
  • 4242 4242 4242 4242
  • 0000 0000 0000 0000
✅ Stripe 官方測試文件中，4242 4242 4242 4242 是用來模擬成功付款的標準測試卡號。選項 A 和 C 分別用於模擬卡片拒絕與无效卡號，不符合「成功付款」的情境。
2. 關於 Stripe Webhook 的簽名驗證，下列敘述何者正確？
  • 簽名驗證可選，因為測試模式下不需要安全性。
  • 簽名驗證用於確保 Webhook 請求確實來自 Stripe，防止偽造請求。
  • 簽名驗證會在 Stripe Dashboard 自動完成，不需在程式碼中處理。
✅ 簽名驗證是安全最佳實踐，透過檢查請求標頭中的 Stripe-Signature，可確認資料未被篡改且來源為 Stripe。選項 A 錯誤，因為即使在測試模式，攻擊者仍可掃描並發送偽造請求；選項 C 錯誤，因為驗證邏輯必須在伺服器端程式碼中實現，Stripe 不會代為驗證。

  2. 使用 AI Agent（如 Claude Code 或 Cursor）生成一個 Next.js API 路由，該路由能接收 Stripe Webhook 並處理 checkout.session.completed 事件，將訂單狀態寫入 Supabase 資料庫。
