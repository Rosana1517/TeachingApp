Phase 5: The Money

身份驗證（Better Auth）

用 AI 快速架起 OAuth 與會話管理，讓 Vibe Coding 也能有企業級的安全認證

1 為什麼 Vibe Coding 需要獨立學「身份驗證」？

在前面的課程中，我們已經用 AI 把資料庫（Supabase）、快取（Redis）、後端 API（Next.js）都串好了，但還有一個關鍵環節一直沒碰——「誰在用這個系統？」。Vibe Coding 的強大來自 AI 能迅速把程式碼生成出來，但如果認證層是錯的，前面做的所有功能都會變成公開的、任何人都能存取的東西。 Better Auth 是 2024 年開始迅速走紅的 TypeScript 型別安全認證庫，它可以獨立於 NextAuth 運作，支援 OAuth（Google、GitHub 等）、Email/Password、OTP 驗證、甚至 2FA。對 Vibe Coding 來說，Better Auth 的好處在於：AI Agent 在生成認證相關的程式碼時，Better Auth 的 TypeScript 型別系統能提供非常具體的提示，讓 AI 不容易「胡亂猜」出錯誤的設定。 在 Vibe Coding 的脈絡中，身份驗證的「角色」是：它既是安全機制，也是資料所有權的界線。沒有它，你的 Vibe 產物就只是玩具；有了它，你才能真正把產品賣出去（所以這門課排在 Phase 5: The Money）。

2 Better Auth 的基本架構與 AI 如何調用它

Better Auth 的核心設計哲學是「零依賴後端、全型別安全」。當你對 AI Agent（比如 Claude Code 或 Cursor）說「幫我加一個 Google OAuth 登入」，Better Auth 的 API 結構會讓 AI 產生出非常有意義的程式碼，而不是憑空猜一個 OAuth 流程。 基本用法很簡單： import { createAuthClient } from "better-auth/client"; import { betterAuth } from "better-auth"; const auth = betterAuth({ emailAndPassword: { enabled: true }, socialProviders: { google: { clientId: process.env.GOOGLE_CLIENT_ID, clientSecret: process.env.GOOGLE_CLIENT_SECRET, }, }, }); AI Agent 在調用 Better Auth 時，會依賴它的 TypeScript 型別來推導出正確的設定結構。如果你寫了 socialProviders: { google: {} } 而忘記放 clientId 和 clientSecret，TypeScript 編譯器會直接报错——這不是軟性的警告，而是硬性的型別錯誤。這對 Vibe Coding 特別重要，因為 AI 生成的程式碼如果在型別上就錯了，後續所有邏輯都會跟著錯。 在 Next.js App Router 中，Better Auth 提供了一套路線組件（Route Handlers），AI 通常會幫你生成一個 api/auth/[...better_auth]/route.ts 檔案來處理所有認證請求。這是 AI 在處理認證時最常見的輸出模式之一。

3 實戰：讓 AI 幫你實現完整的登入/登出功能

接著，在 lib/auth.ts 中建立 auth 實體： import { betterAuth } from "better-auth"; import { nextCookies } from "better-auth/next-cookies"; export const auth = betterAuth({ database: process.env.DATABASE_URL as string, socialProviders: { google: { clientId: process.env.GOOGLE_CLIENT_ID!, clientSecret: process.env.GOOGLE_CLIENT_SECRET!, }, github: { clientId: process.env.GITHUB_CLIENT_ID!, clientSecret: process.env.GITHUB_CLIENT_SECRET!, }, }, plugins: [nextCookies()], }); 然後在 app/api/auth/[...better_auth]/route.ts 建立 API 路由： import { auth } from "@/lib/auth"; import { toNextJsHandler } from "better-auth/next-js"; export const { GET, POST } = toNextJsHandler(auth); 最後在前端使用 @better-auth/client 提供的鉤子： "use client"; import { createAuthClient } from "better-auth/client"; import { useSession } from "better-auth/react"; const client = createAuthClient(); export function LoginPage() { const { data: session } = useSession(); if (session) { return <button onClick={() => client.signOut()}>登出</button>; } return ( <div> <button onClick={() => client.socialSignIn({ provider: "google" })}> Google 登入 </button> <button onClick={() => client.socialSignIn({ provider: "github" })}> GitHub 登入 </button> </div> ); } Vibe 破裂診斷：如果點擊 OAuth 按鈕後沒有跳轉，或跳轉後直接回跳且沒有登入成功，最常見的原因有三個： 1. OAuth 憑證（clientId / clientSecret）沒有設定或設定錯誤。檢查 .env 檔案，確認值存在。 2. 在 Google OAuth 控制台的「授權的 JavaScript 來源」中沒有加入你的開發域名（例如 http://localhost:3000）。 3. Better Auth 的 callbackURL 設定與實際路由不符。Better Auth 預設會把 OAuth 完成後導回 /api/auth/callback/{provider}，如果你的路由結構不同，需要在設定中調整。

4 OAuth 跳轉與權限邏輯——AI 如何理解它

OAuth 的流程對 AI 來說其實很好理解，因為它的步驟非常線性： 步驟 1：使用者點擊「用 Google 登入」按鈕，前端呼叫 client.socialSignIn({ provider: "google" })。 步驟 2：API 路由收到請求後，Better Auth 會導向使用者到 Google 的授權頁面（accounts.google.com/o/oauth2/auth），並附上 client_id、redirect_uri（你的回調地址）、scope（請求的權限範圍，例如 openid email profile）。 步驟 3：使用者在 Google 頁面同意授權，Google 會把瀏覽器導回你的 redirect_uri，帶上一個 code 查詢參數。 步驟 4：Better Auth 的 /api/auth/callback/google 路由收到這個 code，後端用你的 client_secret 向 Google 換取 access_token 和 refresh_token，然後用 access_token 向 Google 的人員資訊 API 抓取使用者的 email、名字等基本資料，最後在資料庫中建立或更新 user 和 account</a> 記錄，並建立會話（Session）。 AI Agent 在生成 OAuth 相關程式碼時，會依賴 Better Auth 的 TypeScript 型別來推導出正確的 OAuth 配置。如果你告訴 AI「要加 GitHub OAuth」，它會生成類似以下的設定： socialProviders: { github: { clientId: process.env.GITHUB_CLIENT_ID!, clientSecret: process.env.GITHUB_CLIENT_SECRET!, scope: "read:user user:email", }, } GitHub OAuth 的 scope 特別重要——如果你只請求 read:user，GitHub 就不會回傳使用者的 email 地址，這會導致某些依賴 email 來建立帳號的邏輯失敗。AI 有時會忽略這一點，需要你明確指出。 Vibe 破裂診斷：如果 OAuth 跳轉後回跳但顯示「找不到使用者」或「email 未驗證」錯誤，檢查： - GitHub 或 Google 控制台中的 App 設定是否開啟了對應的 API 權限。 - 你是否正確設定了 redirectUri（ OAuth 設定頁面中的回調 URL 必須與你的應用程式實際使用的 URL 完全一致，包括 http vs https 和結尾斜線）。 - 在開發環境中，Google OAuth 通常需要將 http://localhost:3000 加入「授權的 JavaScript 來源」白名單，否則 OAuth 流程會直接失敗。

🔬 深入解析：Better Auth 的型別安全為什麼重要
為什麼 Vibe Coding 中「型別錯誤」比「執行時錯誤」更早發現問題更好？

Better Auth 最大的賣點是「零依賴後端 + 全型別安全」。當你對 AI 說「幫我加一個 GitHub OAuth」，AI 生成的程式碼會經過 TypeScript 編譯器驗證。如果 AI 錯寫了 clientId: process.env.WRONG_VAR_NAME，編譯器會在開發階段直接报错，而你根本不需要部署到生產環境才發現問題。 這種「型別安全」在 Vibe Coding 中特別關鍵，原因如下： 第一，AI 生成的程式碼本質上是「猜」出來的，不是經過人工審視的。型別系統是阻止 AI 猜錯的第一道防線——它強制 AI 在生成程式碼時符合 API 的結構，而不是憑感覺寫出看起來像但實際上錯的程式碼。 第二，Better Auth 的 createAuthClient() 和 useSession() 等 API 都有完整的 TypeScript 型別定義。當你呼叫 client.socialSignIn() 時，TypeScript 會要求你傳入合法的 provider 值（例如 "google" 或 "github"），如果你傳了 "google123"，編譯器會直接拒絕。這避免了「AI 以為自己在用 OAuth 但其實在用一個不存在的 provider」這種荒謬但常見的錯誤。 第三，Better Auth 的 betterAuth() 函數的回傳型別是 Auth，它包含了所有已註冊的 API 端點、路由、事件處理器等的完整型別資訊。AI 在生成路由處理器或前端元件時，可以從這個型別中推導出正確的 import 路徑和參數型別，大大降低生成錯誤程式碼的機率。 換句話說，Better Auth 的型別安全不是在「防止 AI 犯錯」，而是在「讓 AI 的錯誤在早期就被發現」。這對 Vibe Coding 的工作流程尤為重要——你希望 Vibe 持續穩定（vibe stable），而不是等到部署後才發現認證邏輯有問題。

1. 以下關於 Better Auth 的描述，哪一個是正確的？
  • Better Auth 只能在 NextAuth 中使用，不能獨立運作
  • Better Auth 是 TypeScript 型別安全的認證庫，可獨立於 NextAuth 使用，並支援 OAuth、Email/Password、2FA 等驗證方式
  • Better Auth 不支援型別安全，因為它完全依賴 JavaScript 運行
✅ Better Auth 是一個獨立的 TypeScript 認證庫，它可以與 Next.js、Express、Hono 等後端框架搭配使用，而不僅限於 NextAuth。它提供完整的型別安全，包括 socialProviders 的設定結構、useSession() 的回傳值型別、以及 createAuthClient() 的方法簽章，這些都能在編譯階段幫助開發者（和 AI Agent）發現錯誤。選項 A 錯誤，因為 Better Auth 不依賴 NextAuth；選項 C 錯誤，因為 Better Auth 是 TypeScript 程式庫，完全支援型別安全。
2. 在 Google OAuth 設定中，哪個步驟最容易導致「OAuth 跳轉後立即失敗」的 Vibe 破裂問題？
  • 使用者在瀏覽器中關閉了第三方 Cookie
  • 在 Google Cloud Console 的「授權的 JavaScript 來源」中沒有加入開發環境的域名（如 http://localhost:3000）
  • 網路頻寬不足導致 OAuth 回應傳輸緩慢
✅ 選項 B 是正確答案。Google OAuth 的「授權的 JavaScript 來源」白名單機制是為了防止跨網站請求偽造（CSRF）和跨來源資源共享（CORS）攻擊。如果開發環境的 URL（如 http://localhost:3000）沒有被加入白名單，Google 會在 OAuth 授權同意畫面之前直接拒絕請求，導致 Vibe 破裂。選項 A 雖然可能影響部分 OAuth 流程（特別是在某些瀏覽器設定下），但 Google OAuth 主要依賴 redirect 而非 cookie 來維持狀態，所以影響較小；選項 C 與 OAuth 流程的正確性無關，只影響體驗速度。
🚀 今日任務

請依序完成以下練習

  1. 任務一：在終端機安裝 Better Auth 相關套件 $ npm install better-auth @better-auth/client @better-auth/react # 如果使用 Bun： $ bun add better-auth @better-auth/client @better-auth/react 確認安裝成功後，在 package.json 的 dependencies 中檢查是否出現 better-auth、@better-auth/client、@better-auth/react。
  2. 任務二：使用 AI Agent（Cursor 或 Claude Code）生成完整的登入/登出頁面 打開 Cursor 或 Claude Code，在聊天視窗中輸入：「在 Next.js App Router 中，使用 Better Auth 實作一個登入頁面，支援 Google 和 GitHub OAuth，並顯示目前登入狀態（使用者名稱和登出按鈕）。請生成 app/(auth)/login/page.tsx 和相關的路由處理器。」 觀察 AI 生成的程式碼，檢查它是否正確使用了 createAuthClient、useSession，以及路由處理器是否使用了 toNextJsHandler。
  3. 任務三：在 Google Cloud Console 建立 OAuth 憑證並設定 .env 前往 console.cloud.google.com，建立一個 OAuth 2.0 Client ID，將 http://localhost:3000 加入「授權的 JavaScript 來源」，將 http://localhost:3000/api/auth/callback/google 加入「授權的重新導向 URI」。然後在專案根目錄建立或編輯 .env 檔案，加入： GOOGLE_CLIENT_ID=你的_client_id GOOGLE_CLIENT_SECRET=你的_client_secret 確認 .env 檔案已被加入 .gitignore，避免憑證意外提交到 Git。
  4. 任務四：除錯挑戰——手動製造並修復一個 OAuth 設定錯誤 在 .env 中故意把 GOOGLE_CLIENT_ID 的値設錯（例如少一個字元），然後運行 npm run dev，點擊 Google 登入按鈕，觀察錯誤訊息。然後修正 GOOGLE_CLIENT_ID，確認 OAuth 流程恢復正常。記錄下這個過程中的錯誤訊息和修復步驟，這能幫助你在未來 Vibe 破裂時更快診斷問題。
