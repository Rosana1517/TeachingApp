Phase 2: Agent Engineering

AI Agent 的 Identity Consistency 與 Persona Drift 控管

讓 Agent 在不同情境下仍能「做自己」而不崩解

1 為什麼這課非寫不可

在我們前面的課程裡，學過 Context Engineering（第 11 課）讓 Agent「記得重要資訊」、也學過 Dynamic Tool Extension（第 38 課）讓 Agent「根據情境即時生成工具」，但這兩件事加在一起，會產生一個隱藏的風險：Identity Drift（身份漂移）。Agent 在運行很長一段時間、或串聯多個子 Agent 之後，它的 persona 可能會悄悄偏離原本設定的樣子——本來應該「謹慎且結構化」的 agent，突然開始寫口語化、情緒化的回覆；本來該專注「寫 Python 腳本」的角色，突然開始講市場策略。vibe broken 有時不是因為程式碼錯，而是因為 agent 連「自己是誰」都搞不清楚了。這一課的目標，就是把 Identity Consistency（身份一致性）變成可設計、可監控、可修復的工程問題，而不是靠運氣。

2 Persona 的分層模型：什麼該動、什麼不該動

設計 persona 的第一步，是學會把 persona 拆成三層，每層的穩定度不同： 核心層（Core Identity）：這層是 agent 的「不可變量」，像是角色定位（「你是一個謹慎的系統架構師」）、基本价值观（「優先保障資料安全性」）、以及語言風格（「回覆使用繁體中文、結構清晰」）。這層應該出現在每次啟動時都會被載入的 system prompt 裡，且不該被 runtime 的上下文輕易覆蓋。 情境層（Contextual Persona）：這層是「可切換」的，例如進入 payment 模組時 persona 會加上「現在你同時扮演 Stripe 整合顧問」，進入 code review 時會加上「現在你同時扮演 TDD 主義者」。情境層依賴 role prompting 機制，在 tool call 前後動態注入。 狀態層（State-Dependent Traits）：這層是「根據長期記憶演化」的部分，例如 agent 在與使用者互動後「學會」的使用者偏好（「他喜歡極簡輸出，不要範例程式碼」）。這層應該存在 knowledge base 裡，而不是直接寫進 system prompt，避免每次都重新訓練 persona。 這三分法的好處是：只有核心層有硬約束，其他層都可以動態調整，這樣 persona drift 就變成「該調整的地方沒調整」或「不該調整的地方被動到」兩個明確的診斷方向，而不是一團模糊的 vibe broken。

3 診斷 persona drift：三種常見的崩解模式

當 vibe 開始不對勁，agent 的 persona 不是突然崩壞，而是按順序出現三種典型模式。學會辨識它們，就能把除錯時間從「整包重寫」縮短到「只修一個層」。 模式 A：Context Bleed（上下文洩漏）——前一輪對話的 tool result 太長或太情緒化，被後續 context window 自動壓縮後殘留了語氣。Agent 本來在寫技術文件，突然開始用「老鐵」「真的絕了」這種口語化形容詞，這就是 context bleed：runtime context 的語氣污染了核心 persona。修復方法是在 context 截斷時加入 tone filter，把非語法內容的語氣詞過濾掉。 模式 B：Multi-Agent Identity Clash（多 Agent 身份衝突）——Lesson 42 學過同步原語，但沒學「當兩個 agent 的 persona 互相矛盾時誰該讓步」。例如 Supervisor Agent 要求「輸出完整報告」，而 Writer Agent 的 persona 是「只給結論不要範例」，兩方同時驅動時就會出現對話邏輯分裂。修復方法是在 role graph 上預先標註 persona 的權重順序， supervisor 的 persona 在跨 agent 溝通時享有 higher priority。 模式 B：Goal Drift（目標漂移）——agent 為了「完成任務」而無意中修改了自己的核心原則，例如本來該「安全優先」，在 deadline 壓力下開始「快速完成優先」。這是 persona 最隱蔽的崩解，因為看起來 vibe 還在，但 agent 已經偷偷改寫了核心約束。修復需要 periodic persona audit：每跑 N 個 step，用一個轻量 evaluator 檢查當前行為是否符合 core persona 的原始定義。

🔬 深入解析：為什麼 context window 壓縮會吃掉 persona
系統提示與上下文的權重競爭，是什麼機制讓 persona 在對話拉長後悄悄偏移？

這背後的機制叫做Attention Decay（注意力衰減）。大型語言模型的 attention 機制在處理長序列時，不是平均分配注意力，而是對「最近出現的內容」賦予更高權重。當 conversation history 超過 context window 的 60% 時，模型為了擠下新的 tool result 或使用者訊息，會自動壓縮最早期的內容——而這個最早期，通常就是 system prompt 裡的 persona 定義。壓縮過程不是一種「錯誤」，而是 attention 架構的必然行為。 更具體地說，大多數 production 用的 agent framework（例如 LangChain、Vercel AI SDK、或 Claude 自身的 function calling）在 truncate context 時，會優先保留「最近 50% 的對話」，把「最早上 50%」中的 system prompt 和早期 tool call 壓縮掉。這意味著：persona 越複雜，它被壓縮掉的風險就越高。當你寫了 800 字的 system prompt，它在 context 長到 80k tokens 時可能只剩 200 字被 attention 到；當你只寫 80 字的核心 persona，它的相對權重反而更穩定。 這也是為什麼 production agent 常見的做法是：核心 persona 不寫在 system prompt 的「末尾」，而是用「前 few tokens」的錨點方式寫入，並配合 periodic re-injection（每跑 N 步把 core persona 重新 inject 進 context）來對抗 attention decay。這就是本課後面要教的「persona audit」的基礎原理。

5 persona drift 的自動化檢查：設計一個 lightweight evaluator

有了防漂移條款還不夠，你還需要一個定期檢視的機制。這個機制的核心思想很簡單：每跑 N 個 tool call（或每 N 分鐘），用一個輕量的「persona evaluator agent」對當前行為做快速評分，發現偏移時觸發 self-correction loop。 Evaluator agent 不需要是頂級模型——用 GPT-4o-mini 或 Claude Haiku 就夠了，因為它的任務只是「打分數」，不是「寫程式」。評分維度建議三個：語氣符合度（Tone Match）、技術深度適中（Depth Match）、核心約束遵守（Constraint Compliance）。每個維度 1-5 分，总分低於 12 就觸發 persona re-anchor。 實作上，可以在 agent loop 裡加一個 Middleware Hook（中介層鉤子），在每次 model response 被送出前執行 evaluator。這個 hook 在 LangChain 裡是 RunnableLambda，在 Vercel AI SDK 裡是 transformResponse middleware。重點是 hook 不要阻塞主流程——evaluator 跑完只要分數低於閾值，才把 persona reminder 追加到接下來要 sent 的 context 裡，而不是直接改掉模型的回覆。

1. 以下哪一項最準確描述了「Context Bleed」在 persona drift 中的角色？
  • context bleed 是指 system prompt 被截斷後，模型強制插入新的 persona 定義，造成身份覆蓋
  • context bleed 是指 runtime context（tool result、對話歷史）中的語氣或風格污染了 core persona，讓 agent 在不該變的地方變了
  • context bleed 是指多個 agent 之間的 persona 衝突，導致 supervisor agent 無法決定要用哪個角色的輸出
✅ A 描述的是「persona overwrite（ persona 覆蓋）」而非 context bleed；C 描述的是「multi-agent identity clash（Lesson 42 的延伸主題）。Context bleed 的根源是 runtime context 的語氣洩漏到核心 persona，B 的描述最精確：tool result 或對話歷史帶著口語化語氣進入 context window，壓縮時把這些語氣殘留下來，agent 在後續回覆中不自覺地使用了這些語氣，這就是 context bleed 的機制。

1. 根據 Deep Dive 中解釋的「Attention Decay」機制，以下哪一個做法最能直接對抗 persona 被壓縮掉的風險？
  • 把 system prompt 寫得越長越好（例如 2000 字），讓核心 persona 在壓縮後仍有足夠文字保留

✅ A 是錯誤的——prompt 越長，在 context 壓縮時被截掉的絕對量越大，反而加速 drift；這是反直覺但重要的發現。C 描述的是從 knowledge base 動態載入，但這依賴 RAG pipeline 的穩定性，且 knowledge base 的檢索結果不受 attention 錨點保護。B 是正確做法：把核心 persona 保持在 context 開頭的錨點位置（高 attention 權重），並用 periodic re-injection 對沖 attention decay——這正是 production agent 的標準做法，也是本課 Deep Dive 中明確提出的機制。
🚀 今日任務

請依序完成以下練習

  1. 任務一：建立防 persona drift 的 starter prompt 打開你的專案根目錄，建立或編輯 .cursorrules（Cursor 使用者）或 CLAUDE.md（Claude Code 使用者），把本課第 4 節的三層 persona 模型寫進去，特別是要加入那三條 Anti-Drift Clauses。不要用 copy-paste，改成符合你自己專案風格的版本。
  2. 任務二：實測 persona drift 用 Cursor 或 Claude Code 開啟一個真實的 Next.js 專案，先讓 agent 幫你寫一個小功能（例如 Supabase 的 CRUD），然後在接下來的 10-15 輪對話裡持續跟它討論同一個主題。觀察 agent 的語氣有沒有開始變口語化、變情緒化，或是開始講與技術無關的內容。把觀察到的漂移現象記錄下來（文字即可，不用截圖）。
  3. 任務三：設計一個 lightweight persona evaluator 用 Claude Code 或 Cursor 幫自己寫一個簡單的 evaluator script（可以用 Python 或 TypeScript），功能很簡單：讀取最近 N 則 agent 回覆，用一個輕量模型評分「語氣是否符合核心 persona」。評分結果輸出成 JSON，包含 tone_score、depth_score、constraint_score 三個欄位。這不是 production 級的 evaluator，只是練習目的，能用正則或關鍵字做基本比對就夠了。
  4. 任務四：加入 periodic re-injection hook 在你的 agent 工作流程裡（可以是一個簡單的 Node.js/Bun 腳本，或用 Vercel AI SDK 的 transformResponse middleware），實作每 5 次 tool call 就把 core persona 的前 3 句重新 inject 進 context 的機制。觀察 re-injection 前後 agent 的回覆語氣有沒有穩定下來。這是一個可驗證的對照實驗，請記錄 before/after 的差異。
