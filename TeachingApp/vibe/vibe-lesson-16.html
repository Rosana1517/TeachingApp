Phase 3: The Brain

Coding Agent 與檔案系統架構

把檔案系統從「儲存區」升級為 Agent 的「外部大腦」

🧠 架構核心：為什麼是檔案？

在 Vibe Coding 的實戰中，業界驗證過最強的通用 Agent 範式，就是「會寫代碼的 Agent」加上「對檔案系統的完全控制權」。為什麼 Claude Code、Cursor 或 Devin 都選擇代碼執行、檔案讀寫與搜尋這三種工具作為核心？答案很簡單：代碼是人類最精密、最無歧義的語言。相較於讓 Agent 在聊天框裡口頭描述修改方案（容易產生誤解），直接讓它修改 .js 或 .tsx 文件，然後執行測試，是目前可擴展性與準確性最高的路徑。檔案系統在這裡不再只是靜態的儲存庫，而是成為了 Agent 的「工作記憶」與「思維鏈（Chain of Thought）」的外掛硬碟。

📂 檔案系統作為「暫存記憶」

當 Vibe 崩潰（例如編譯錯誤或邏輯跑偏）時，修復的關鍵往往不在於換一個更聰明的 Prompt，而在於如何利用檔案系統來承載上下文。成熟的 Agent 會在執行複雜任務時，先在專案根目錄建立一個 .vibe-context.md 或 plan.md，將當前目標、已完成的步驟、遇到的陷阱寫進去。這樣做有兩個巨大好處：第一，它繞過了 LLM 的上下文視窗限制，將長期狀態存在磁碟上；第二，當 Agent 發生「幻觉」或迷失方向時，你可以直接打開這個檔案查看它的計畫，甚至手動修正其中的錯誤步驟，讓 Agent 從「被修正後的計畫」繼續執行。這就是將檔案系統當作「外部大腦」的實務應用。

🩺 診斷與修復 Vibe 破裂

當 Vibe 破裂，Agent 陷入死迴圈（Loops）時，請執行以下診斷步驟：1. 檢查檔案mtime與內容：看 Agent 最近修改了哪些文件，確認它是否真的在解決問題，還是在亂改無關代碼。2. 引入「觀察者」檔案：在專案中建立一個 memory.md，要求 Agent 每完成一個子步驟，就回寫一行狀態到這個檔案。如果狀態沒有更新，代表 Agent 卡住了。3. 干預工具權：如果 Agent 過度依賴 bash 卻不寫代碼，檢查它的工具權限設定，強制它使用 write_file 而非手動 echo 來修改代碼，確保變更可追蹤。

3 實戰：讓 Agent 使用 Plan 檔案

以下是一個真實的實務場景：要求 Claude Code 基於一個計畫檔來重构代碼。這能訓練 Agent 先思考、再執行，避免盲目改碼。

# 1. 先建立計畫檔，作為 Agent 的「記憶體」 $ echo "TODO: 將 src/utils.js 重构為 TypeScript，並更新測試" > plan.md # 2. 啟動 Claude Code，並指定它參考計畫檔 $ claude -p "請根據 plan.md 的指示，執行重构任務。每完成一步請更新 plan.md 的狀態。" # 3. 觀察 Agent 的行為：它應該先讀取 plan.md，然後產生 .ts 文件，最後執行測試 Reading plan.md... Found task: Refactor src/utils.js to TypeScript. Creating src/utils.ts... Running tests... All tests passed. Updating plan.md... # 4. 檢查最終的 plan.md，確認 Agent 是否忠實執行了計畫 $ cat plan.md [✓] 建立 src/utils.ts [✓] 更新測試檔案 [✓] 清除旧版 src/utils.js
🔬 深入解析：為什麼是這三種工具？
為什麼 Claude Code 不選擇資料庫或 GUI 操作，而是死磕檔案系統？

這背後是「最小惊讶原則」與「可觀測性」的考量。資料庫操作需要連接字串、遷移腳本，環境差異極大；GUI 操作則難以透過文字 LLM 精確控制。相比之下，檔案系統是程式碼的唯一源頭。當 Agent 修改了一個 TypeScript 文件，整個生態系（TypeScript 編譯器、ESLint、Vitest、Next.js 開發伺服器）會自動響應這些變更。這種「改檔即生效」的鏈式反應，讓 Agent 可以用極少的工具調用，實現極大的系統影響。此外，檔案系統是「持久化」的，這意味著 Agent 的中斷狀態可以被保存，這對於長時任務至關重要。選擇檔案系統作為核心，本質上是選擇了「最通用、最穩定、最可追溯」的介面。

✏️ 小測驗

請先回答，再點擊「查看答案」

1. 在 Vibe Coding 中，為什麼建議讓 Agent 將計畫寫入檔案（如 plan.md）而非僅依賴聊天上下文？
  • 因為聊天上下文佔用 GPU 記憶體，寫入檔案可以節省計算成本。
  • 因為檔案系統提供了持久化記憶，能突破 LLM 上下文視窗限制，並允許人類干預與追蹤。
  • 因為 LLM 無法記住超過 10 行的對話，寫入檔案是為了訓練模型的短期記憶能力。
✅ A 選項錯誤，雖然節省上下文有間接好處，但核心原因是持久化與可觀測性，讓 Agent 能在多次交互中保持狀態，並讓開發者隨時查看計畫進度。C 選項錯誤，LLM 的上下文視窗遠大於 10 行，寫檔案是為了擴展到整個專案層級的記憶，而非訓練短期記憶。
2. 當 Agent 陷入「修改代碼但測試一直失敗」的死迴圈時，以下哪種診斷方式最有效？
  • 直接重置整個專案的 git 歷史，強制 Agent 從零開始。
  • 檢查檔案系統的 mtime（修改時間）與內容變更，確認 Agent 是否真的在解決問題，並手動修正 memory.md 中的錯誤步驟。
  • 更換一個更強的 LLM 模型（如從 Claude 3.5 換到 GPT-4o），因為這是模型智商不夠的問題。
✅ A 選項過於極端且會丟失工作成果。C 選項錯誤，死迴圈通常是工具使用策略或上下文缺失的問題，而非單純的模型智商問題，換模型無法解決架構缺陷。B 選項正確，因為透過觀察檔案變更與計畫檔狀態，可以精確定位 Agent 是卡在「理解錯誤」還是「執行錯誤」，從而進行有效干預。
🚀 今日任務

請依序完成以下練習

  1. 建立你的「外部大腦」：在任意一個 Next.js 專案根目錄，建立一個 TODO.md 檔案，寫下三個你想讓 AI 完成的任務（例如：新增一個組件、修復一個 Bug、更新測試）。
  2. 實戰觀察：使用 Claude Code 或 Cursor Composer，輸入指令「請閱讀 TODO.md 並開始執行第一個任務，每完成一步請在 TODO.md 中打勾」。觀察 AI 是如何讀取、修改檔案並更新計畫的。
  3. 人為干預：在 AI 執行過程中，手動修改 TODO.md，將第一個任務刪除，並新增一個錯誤的任務描述。觀察 AI 是否會依據新的檔案內容調整行為，還是會固執地執行舊的邏輯。
  4. 診斷演練：故意寫一個有錯的 package.json 或引入一個會報錯的依賴，觀察 Agent 是如何透過讀取錯誤訊息檔案（如 npm-debug.log 或終端輸出）來嘗試修復的。記錄下它使用的工具順序。
