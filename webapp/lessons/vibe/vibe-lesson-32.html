Phase 4: Agent Engineering Deep Dive

課程主標題：AI Agent 的成本控管與 Token 優化

掌握 token 計費邏輯，在 vibe coding 中避免驚人帳單並提升效率

1 為什麼成本控管是 Vibe Coding 的必修課

在 Vibe Coding 的工作流中，我們習慣讓 AI Agent（例如 Claude Code、Cursor、Bolt 等）大量處理程式碼產生、除錯、重構等任務。然而，這些工具的背後都是按 token 計費的 LLM API。如果你從來沒注意過自己的使用情況，很可能會在某天看到一張讓你大吃一驚的帳單。成本控管不是要你限制 Agent 的能力，而是要你學會策略性地使用它——用更少的 token 達到相同甚至更好的效果。這涉及四個核心面向：輸入優化（減少無謂的上下文）、輸出控制（避免冗長回應）、快取策略（重複請求的 cost 節省）以及計費監控（實時掌握消耗）。

2 Token 計費的現實：你正在付錢的是什麼

大多數商業 LLM API（OpenAI、Anthropic、Google、OpenRouter 等）都採用 token 計費制。一個 token 大約等於 0.75 個英文單字或 0.5 個中文字。當你發送一段 prompt 時，你支付的是「輸入 token」；當模型產生回答時，你支付的是「輸出 token」。兩者單價不同——通常輸出 token 比輸入 token 貴 2～5 倍。舉例來說，Claude 3.5 Sonnet 的輸入價格約為每百萬 token $3，輸出價格約為每百萬 token $15。這意味著一個簡單的對話如果上下文累積到 10 萬輸入 token + 1 萬輸出 token，成本就是 $3.15，看起來不多，但若每天重複使用，一個月就可能超過 $100。

3 輸入優化：減少無謂的上下文消耗

上下文工程在第 13 課已經講過，但從成本角度重新審視，你會發現許多開發者正在無意義地燒錢。最常見的成本黑洞包括：① 每次都把整個專案結構塞進 prompt；② 在對話中重複貼上相同的程式碼片段；③ 沒有使用工具封裝而是一次次手動貼上檔案內容。具體優化策略：使用 .cursorrules 或 .claude/rules 設定全域提示，避免每次重複寫相同指示；善用工具呼叫讓 Agent 自行讀取檔案，而不是你貼上；使用 /compact（Claude Code）或 /clear 定期清理對話上下文；對於大型檔案，用 sed、grep 或 ripgrep 等 CLI 工具先定位再讓 Agent 處理特定區段，而不是一股腦丟進去。

4 輸出控制：避免冗長回應的成本黑洞

許多開發者發現，同樣的問題，不同的模型或參數設定，輸出的 token 量可以差上 10 倍。例如讓 Claude 解釋一段程式碼，它可以產生 500 字的詳細教學，也可以產生 3 行的簡潔說明。控制輸出長度的核心方法：在 system prompt 中明確設定回應格式限制，例如「請用 JSON 格式輸出」或「回答不超過 3 行」；對於程式碼產生，要求 Agent 直接輸出可執行的程式碼而不是教學式解釋；使用 /compact 命令將冗長的歷史對話壓縮成精簡的摘要，然後基於摘要繼續；對於只需要简单確認的任務，使用更快的便宜模型（如 Claude 3.5 Haiku 或 GPT-4o-mini）而非昂貴的旗艦模型。實際案例：如果你只是讓 Agent 檢查一段程式碼是否有安全漏洞，用 Haiku 模型可能只要 $0.25，但用 Sonnet 模型可能花 $2.50，而效果幾乎相同。

5 快取策略：被低估的成本節省武器

所有主流 LLM API 都提供某種形式的提示快取（Prompt Caching）。Anthropic 的「Prompt Caching」是最成熟的實作——當你發送與上次相同的 prefix（例如相同的 system prompt + 相同的檔案內容），快取命中時輸入 token 的價格可以降到原来的 1/10。具體來說，Claude 3.5 Sonnet 的快取命中價格是每百萬 token $0.30，而非快取時是 $3.00。如何最大化快取命中率：① 保持 system prompt 絕對穩定，不要每次改變；② 將不常變動的上下文（如程式碼架構說明、專案規範）放在 prompt 的最前面，這樣即使後續內容變化，前面的固定部分仍能命中快取；③ 使用相同的模型版本，混用不同模型會導致快取失效；④ 對於相同檔案內容，確保編碼和格式一致，任何微小差異都會導致快取失效。注意：OpenAI 也有類似的快取功能（Context Caching），但實作細節不同，且僅限 GPT-4o 和 o 系列模型。

6 計費監控：實時掌握你的 token 消耗

不知道自己在花多少錢，是成本控管失敗的主因。不同工具提供的監控方式：Anthropic Console 提供完整的 API 使用紀錄和成本試算；OpenAI Platform 有詳細的使用量儀表板；Cursor 內建 usage 面板（右上角點擊你的頭像可以看到本月使用量）；Claude Code 的 /cost 命令會顯示當前對話的 token 消耗和預估成本；OpenRouter 提供跨模型的統一計費介面。建立監控習慣：① 每天開始工作前看一眼成本儀表板；② 設定預算警報（Anthropic 和 OpenAI 都支援設定月度預算上限）；③ 定期檢視哪些專案或功能消耗的 token 最多，找到優化機會；④ 對於個人開發者，考慮使用 .env 中的 ANTHROPIC_API_KEY 或 OPENAI_API_KEY 對應的免費層额度作為緩衝。

7 Vibe 破裂診斷：當成本超支時的緊急處理

當你發現 token 消耗異常時，這通常意味著你的 Agent 正在做某些低效的事情。常見的 vibe 破裂情境與修復方法：① **對話過長導致成本飆升**：使用 /compact 或 /clear 重置上下文，然後用精簡的 system prompt 重新開始；② **Agent 陷入無限迴圈**：設定 max_turns 或使用 Agent 工具時加入 timeout 限制；③ **大量檔案被錯誤地載入上下文**：檢查你的 .gitignore 和工具的 ignore 設定，確保 node_modules、.next、dist 等目錄不被包含；④ **使用了過昂貴的模型**：建立模型切換快捷鍵或設定，讓常見任務使用 Haiku/GPT-4o-mini 等便宜模型；⑤ **快取失效**：檢查你的 system prompt 是否被意外修改，以及檔案編碼是否一致。診斷命令：在 Claude Code 中使用 /cost 查看即時成本；在 Cursor 中使用 Cmd+Shift+P → 「Cursor: Show Usage」查看詳細數據。

🔬 深度解析：為什麼大上下文不等於好結果
為什麼越來越多 token 反而讓 Agent 變笨，還让你變窮？

這涉及 LLM 的注意力機制（Attention Mechanism）的本質限制。Transformer 架構的注意力計算複雜度是 O(n²)，其中 n 是序列長度。雖然這不直接解釋「為什麼長上下文變笨」，但它確實解釋了為什麼更長的上下文需要更多的計算資源和更高的成本。真正的原因是：當上下文過長時，重要的資訊會被「稀釋」。模型需要在成百上千個 token 中尋找相關資訊，這增加了「注意力分散」的機率。此外，長上下文中的矛盾資訊（不同檔案中的不同程式碼風格、過時的註解等）會導致模型產生不一致的輸出。從成本角度的進一步解釋：即使你支付更多 token，模型的準確率也不一定會提升——有時反而下降。這意味著你同時失去了成本效益和結果品質，形成雙重損失。最佳實踐是保持上下文精簡且相關，使用 RAG（第 18 課）和工具呼叫（第 15 課）讓 Agent 在需要時才獲取特定資訊，而不是一股腦塞入所有資料。

  1. 查看並記錄你目前使用的 AI 工具（Cursor/Claude Code/Copilot 等）的當前 token 使用量和成本，找出你最常使用的模型及其計費標準
  2. 在你的主力專案中，檢查是否有任何大型目錄（如 node_modules、.next、dist）被意外包含在 Agent 的上下文處理範圍內，並修正相關設定
