Phase 3: The Brain

Agent 核心公式：LLM + 上下文 + 工具

拆解智能體的智慧三元組，理解 Vibe Coding 的自動化邏輯

🧠 Agent 核心公式拆解

Agent 的本質可以歸納成一個公式：Agent = LLM + 上下文 + 工具。LLM 是決策大腦，負責理解意圖、規劃步驟與生成回應；上下文是視野，決定 Agent 能看到哪些資訊與歷史；工具是手腳，讓模型能夠實際與外部環境互動、讀寫檔案或執行程式。在 Vibe Coding 中，這個公式解釋了為什麼有時候 Agent 看起來很聰明卻做不出正確功能——通常不是模型不夠強，而是上下文給錯了，或是工具沒有正確定義。理解這個三元組，能幫助你快速定位問題發生在哪個層面，而不是盲目重複提問。

1 LLM：決策核心與限制

現代 LLM 本質上是一個極其強大的「文字接龍」引擎，透過海量文本訓練學到了語言結構與部分世界知識，但模型本身沒有主動執行動作的能力。在 Agent 架構裡，LLM 扮演的是規劃者的角色：根據你給的指令與工具說明，決定下一步要調用哪個工具、傳入什麼參數。換句話說，模型越強，規劃越精準；但就算是最先進的模型，若沒有正確的上下文與可用的工具，它也只會產生「看似合理卻無法執行」的輸出。在 Vibe Coding 中，選擇合適的模型會直接影響開發效率與輸出品質，例如 Claude 3.5 Sonnet 或 GPT-4o 在程式碼生成與工具調用上表現突出。

2 上下文：視野決定理解深度

上下文是 Agent 能看見的「資訊窗口」，包含你的提示詞、工作區檔案內容、對話歷史、工具輸出結果等。上下文的設計稱為 Context Engineering，目標是讓模型在不超出 token 限制的前提下，看到最相關且最有價值的資訊。一個常見的錯誤是丟入過多的無關檔案，導致模型注意力分散；另一個極端是上下文太少，模型只能憑記憶猜測，容易產生幻覺。在 Vibe Coding 流程中，善用 `.cursorrules`、`.clinerules` 或系統提示詞來設定開發上下文，能大幅減少無效輸出與重複說明。

3 工具：從思考到執行的橋樑

工具是讓 Agent 從「說」變成「做」的關鍵元件。透過工具定義，模型可以調用程式碼執行、檔案讀寫、網路請求或專用函數。在 Claude Code、Cursor Agent 或 Bolt 等工具型 Agent 裡，工具清單通常包含 `ReadFile`、`WriteFile`、`Bash`、`WebFetch` 等內建操作，也可透過 MCP（Model Context Protocol）擴展更多能力。當你發現 Agent 一直「只說不做」或輸出與需求不符，很可能是工具定義不完整或權限設定有問題。工具設計的原則是：明確的名稱、清晰的參數說明、可預期的輸出格式，這能讓模型更準確地選擇與呼叫工具。

🔬 深入解析：為什麼同一顆模型換 Harness 表現天差地遠？
模型能力相同，為何 Claude Code 比聊天框更能完成複雜開發任務？

同一個 LLM 背後的推理能力是一樣的，但「表現差異」來自三個 Harness 層面的設計：上下文管理策略、工具調用機制與錯誤恢復循環。聊天視窗通常只把使用者的輸入當作單一提示，模型無法持續保留執行狀態；而專業 Coding Agent 會把工作區狀態、工具輸出、歷史決策都納入上下文視窗，形成一個連續的執行圖譜。此外，Harness 會定義工具調用的觸發條件與參數驗證，避免模型產生格式錯誤的工具呼叫。當 Vibe 破裂時，若錯誤訊息是工具參數錯誤，代表 Harness 的工具定義需要修正；若是模型邏輯錯誤，則需要調整上下文或提問策略。
