Phase 4: Advanced Agent Engineering

課程主標題：AI Agent 的 Tool Dependency Graph 與執行序控管

讓 Agent 知道「先做 A 再做 B」，而不是一股腦丟出所有工具呼叫

1 為什麼工具執行序這麼重要？

在 Vibe Coding 的實戰中，你常常會看到 Agent 同時呼叫五個工具、七個工具，看起來很有條理，但最後結果卻爛掉。為什麼？因為工具之間有依賴關係：工具 B 需要工具 A 的輸出、工具 D 要先檢查工具 C 是否成功，但 Agent 沒有這個認知，它把全部工具一齊送出去，導致執行結果無法串接、部分失敗、甚至重複執行。Tool Dependency Graph（工具依賴圖）就是解決這個問題的工程方法：把 Agent 擁有的工具集合，畫成一張有向圖，讓 Agent 知道哪些工具可以並行、哪些必須順序執行。這不是單純的「效率優化」，而是「正確性保證」——在 Vibe Coding 中，正確的執行序才是 vibe 穩定的基石。

2 AI Agent 如何理解與使用 Tool Dependency Graph？

當你用 Claude Code、Bolt 或自建的 LangGraph/LangChain agent 時，Agent 不會自動知道工具之間的依賴關係，除非你明確地告訴它。最常見的實作方式是透過 function calling schema 的擴充字段（例如 LangGraph 的 Node + Edges 架構），讓每個工具「節點」定義它的輸入依賴，以及執行完之後的「下一站」是哪些工具。Agent 的核心循環會讀取這張圖，動態決定下一步要呼叫哪個工具、是否要等待前一個工具的結果。在 Vibe Coding 的場景中，你通常不需要手寫這套圖，而是用 LangGraph 或 Temporal 這類框架來建立圖結構，讓 Agent 在執行時自動追蹤當前節點，並在工具失敗時沿着錯誤邊跳到 recovery node。

3 常見 Vibe 破裂情境與診斷

當 Agent 的工具執行序出錯時，Vibe 破裂的症狀非常具體：症狀一：工具 B 收到 undefined 的參數——因為工具 A 還沒執行完，B 就被呼叫了。症狀二：同一個工具被重複呼叫——Agent 沒有記住工具 A 已經執行過，在下一輪 context 中又決定呼叫它。症狀三：執行順序錯亂導致中間結果丟失——例如先呼叫了「讀取資料庫」又才呼叫「建立連線」，連線還沒建立就去讀資料庫，必然失敗。診斷方法很直接：把 Agent 的 tool_calls 列表依時間排序，檢查每個工具的輸入參數是否包含前一個工具的輸出，如果發現參數引用了不存在的變數，那就是依賴圖沒有正確建立或 Agent 沒有追蹤圖的節點狀態。

🔍 對照：並行 vs 串行 vs 條件式執行

不同執行策略適合不同場景，選錯策略會直接導致 vibe 破裂。

並行執行（Parallel）
适合工具之间完全独立的情况， 例如同时调用 weather API 和 news API， 两者结果互不影响，可以一次送出 多个 tool_call，并行等待结果。 缺点：如果工具 B 需要工具 A 的 输出，并行会导致 B 收到 undefined。
串行執行（Sequential）
适合工具之间有明确依赖关系的情况， 例如先 call get_user()，拿到 userId 后再 call get_orders(userId)。 LangGraph 中用 SequentialFunction 或 Node + Edge 明确指定顺序。 优点：结果一定正确；缺点：速度较慢。
🛠️ 帶指令範例：建立 LangGraph 工具依賴圖

以下是一個真實可運行的範例，展示如何用 LangGraph 建立有依賴關係的工具圖。這個範例中的工具 A 和工具 B 有明確的依賴關係，Agent 必須先執行 A，再執行 B。

$ npm install langgraph @langchain/core added 42 packages in 3.2s # 建立兩個工具，B 依賴 A 的輸出 from langchain_core.tools import tool from langgraph.graph import StateGraph, START, END from typing import TypedDict class AgentState(TypedDict): step: str user_id: str order_count: int @tool def create_user(name: str) -> str: """Create a new user and return the user ID.""" return f"user-{name}-123" @tool def get_order_count(user_id: str) -> int: """Get the total number of orders for a user.""" return 42 # 定義圖的節點 def create_user_node(state: AgentState) -> AgentState: result = create_user.invoke({"name": state["step"]}) return {"step": result, "user_id": result} def get_orders_node(state: AgentState) -> AgentState: result = get_order_count.invoke({"user_id": state["user_id"]}) return {"step": state["step"], "order_count": result} # 建立圖並連接節點 graph = StateGraph(AgentState) graph.add_node("create_user", create_user_node) graph.add_node("get_orders", get_orders_node) graph.add_edge(START, "create_user") graph.add_edge("create_user", "get_orders") graph.add_edge("get_orders", END) app = graph.compile() Graph compiled successfully.
🔬 深入解析：Tool Dependency Graph 的核心原理
為什麼 Agent 需要一張圖來管理工具執行，而不是直接用 if-else 寫死順序？

Tool Dependency Graph 的本質是「狀態機 + 有向圖」的結合。每一個工具被視為圖中的一個節點（Node），工具之間的依賴關係是圖中的邊（Edge）。當 Agent 執行到某個節點時，它會根據當前狀態（State）決定下一步走哪條邊。這不是簡單的時間順序問題，而是「條件依賴」問題——工具 B 可能需要工具 A 的成功結果，也可能需要工具 A 的失敗結果來決定走哪條路徑。用 if-else 寫死順序會有三個致命缺點：第一個缺點是無法處理循環，例如工具 A 失敗時需要重新執行工具 B 再試一次 A，if-else 寫不出這種循環邏輯。第二個缺點是無法處理條件分支，工具 A 的結果如果是 positive 就走路徑 X，如果是 negative 就走路徑 Y，if-else 可以寫但會迅速變成難以維護的 nested if。第三個缺點是無法動態擴展，當新增一個工具時，你需要改動所有相關的 if-else 邏輯，而圖結構只需要新增一個 Node 和對應的 Edge。在 Vibe Coding 的實戰中，這張圖通常由 LangGraph、Temporal 或自建的 state machine 來維護，Agent 的核心循環只是「讀取當前節點 → 執行工具 → 讀取狀態 → 決定下一節點」，不需要知道整個圖的結構，這正是解耦的好處。

✏️ 小測驗

請先回答，再點擊「查看答案」

1. 當工具 B 依賴工具 A 的輸出時，以下哪種執行策略會導致 vibe 破裂？
  • 串行執行（Sequential），先執行 A 再執行 B
  • 並行執行（Parallel），同時呼叫 A 和 B
  • 條件執行，先執行 A，根據 A 的結果決定是否執行 B
✅ 並行執行會同時送出 A 和 B 的工具呼叫，但 B 的輸入參數需要 A 的輸出，在 A 還沒執行完時 B 已經被呼叫，導致 B 收到 undefined 或錯誤的參數，這是典型的 vibe 破裂情境。串行執行和條件執行都能確保 A 的結果在 B 執行前就存在。
2. 以下哪個是 Tool Dependency Graph 相對於 if-else 順序邏輯的主要優勢？
  • 執行速度更快，因為圖結構有更快的記憶體存取
  • 可以表達循環依賴和條件分支，而不需要複雜的 nested if
  • 不需要定義 State，Agent 可以直接在圖中流動
✅ Tool Dependency Graph 的核心優勢在於可以用圖的結構（Node + Edge）自然地表達循環依賴（例如 retry 邏輯）和條件分支（例如 success edge vs error edge），而不需要用 if-else 寫出難以維護的 nested 邏輯。執行速度並不是主要優勢，因為圖的遍歷本身也有開銷。State 仍然是必要的，因為每個節點的執行結果都需要更新狀態。
