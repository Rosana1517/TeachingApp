Phase 3: The Brain

RAG 檢索增強生成基礎

打破訓練時效限制，從專案知識庫精準取用答案

1 RAG 是什麼？為什麼 Vibe Coding 需要它？

RAG（Retrieval-Augmented Generation，檢索增強生成）的核心概念很直白：讓 AI 在回答之前，先去查閱相關資料，而不是只靠訓練時期的記憶瞎猜。在 Vibe Coding 的情境中，Agent 每天要處理成千上萬個專案檔案——README、程式碼註解、設計文件、舊的討論記錄。如果每次詢問都只靠 LLM 內部參數，不僅容易過時，也很難精準對應到你專案的特定實現細節。RAG 讓 Agent 擁有一個「外置大腦」：先把相關內容從知識庫中取出，塞進上下文窗口，再讓 LLM 基於這些真實資料回答。這樣做的好處是，答案會貼近專案現實，且你能清楚追溯 AI 是從哪裡找到答案的。

2 AI Agent 是如何調用 RAG 的？

一個典型的 RAG 流程包含三個步驟：查詢 → 檢索 → 生成。當你向 Agent 提問時，Agent 並不會立刻回答，而是先產生一個搜尋請求（query），用這個請求去查詢你的知識庫。知識庫通常是一座向量資料庫（Vector Database），裡面存著你專案各類文件的「嵌入向量」（Embedding）。Agent 會將你的問題轉換成同樣的向量表示，然後在資料庫中找最相似的片段。找到相關內容後，Agent 會把這些片段作為額外上下文追加到提示詞中，最後由 LLM 綜合原始問題與檢索到的資料，給出有憑有據的答案。這整個過程對你來說是無縫的，但背後涉及 Embedding 轉換、相似度計算與上下文拼接等關鍵技術。

3 實戰：觀察 RAG 行為

現在我們來實際體驗一次 RAG 的運作。請打開你的專案，並確保裡面已經有一些技術文件（例如 README.md、doc 資料夾下的說明檔）。接著使用 Claude Code 或 Cursor，提出一個需要查閱專案內部文件才能準確回答的問題。例如：「根據專案文件，我們目前用的狀態管理方案是什麼？請引用具體的檔案路徑。」觀察 AI 的回應過程，它應該會先進行搜尋動作，然後再給出答案，並且答案中會明確指出資訊來源的檔案路徑。如果 AI 沒有先搜尋就直接回答，或者給出的答案沒有引用任何專案內文件，這就是一個 vibe broken 的訊號，代表 RAG 流程可能沒有正確觸發或檢索失敗。

🔬 深入解析：Embedding 與向量搜尋
為什麼文字可以被轉換成向量，並且計算相似度？

RAG 的效能關鍵在於 Embedding 模型與向量搜尋。Embedding 模型（如 OpenAI 的 text-embedding-ada-002）會將一段文字轉換成一個固定長度的數值向量，這個向量的每個維度代表文字在某个語義維度上的得分。例如，「汽車」和「車輛」這兩個詞在向量空間中會靠得很近，因為它們的語義相似。當我們把專案的每一份文件切割成小的 chunk，並用同一個 Embedding 模型將它們轉換成向量後，就能存入向量資料庫（如 Pinecone、Weaviate 或本地端的 Chroma）。當使用者提問時，問題也會被轉成向量，然後資料庫使用相似度演算法（常見的是余弦相似度）找出與問題向量最接近的 document 向量。這種方法能夠捕捉語義上的相似性，而不只是關鍵字匹配，因此即使問題和文件中的用詞不完全相同，也能找到相關內容。

4 常見 RAG 問題與修復

當 RAG 出現 vibe broken 時，通常有幾種典型症狀：檢索不到相關內容、檢索到錯誤內容、答案缺乏引用來源、或上下文窗口被填滿後遺漏關鍵資訊。針對這些問題，我們可以從幾個方向診斷與修復：第一，檢查 Embedding 模型是否與向量資料庫的設定一致，如果兩邊用不同的模型，產生的向量無法比較，檢索必然失敗。第二，調整 chunk 大小與重疊率，chunk 太大可能雜訊多，chunk 太小可能缺乏上下文，通常建議在 500~1000 個 token 之間並保留 100~200 的重疊。第三，優化查詢轉換（query transformation），有些系統會將原始問題改寫成更适合搜尋的形式，這能大幅提升檢索準確性。第四，考慮使用混合搜尋，結合關鍵字搜尋（BM25）與向量搜尋，取兩者優點。

5 RAG 與 Function Calling 的協作

在進階的 Agent 架構中，RAG 並不是孤立運作的，它經常與 Function Calling 配合使用。例如，Agent 可以先透過 Function Calling 調用一個 search_documents(query) 工具，這個工具內部就會執行 RAG 檢索，然後將結果回傳給 LLM。這種設計的好處是將檢索邏輯封裝成一個明確的工具，Agent 可以重複使用，並且可以對工具加入參數驗證、結果過濾等邏輯。另一個協作模式是將 RAG 結果作為 Function 的回傳值，然後 LLM 根據回傳值決定下一步動作，比如是進一步搜尋、直接回答、還是觸發其他工具。這種分工讓 Agent 的行為更可預測，也更容易除錯。

1. 在 RAG 流程中，以下哪個步驟是首先發生的？
  • LLM 直接根據訓練記憶生成答案
  • 將問題轉換成向量並搜尋知識庫
  • 將所有專案檔案讀入上下文窗口
✅ RAG 的第一步是檢索（Retrieve），也就是將使用者問題轉換成向量，並在向量資料庫中尋找最相似的內容片段。選項 A 描述的是不使用 RAG 的純 LLM 回答方式，选项 C 則是低效的做法，因為將所有檔案都讀入會撐爆上下文窗口，也不是 RAG 的設計目的。
2. 以下哪個做法不能有效提升 RAG 檢索準確性？
  • 調整 chunk 大小與重疊率
  • 使用與 Embedding 模型不一致的向量資料庫
  • 結合關鍵字搜尋與向量搜尋
✅ 使用與 Embedding 模型不一致的向量資料庫會導致檢索失敗，因為不同模型產生的向量空間不同，無法進行有效的相似度計算。選項 A 和 C 都是業界公認的有效優化手段。
