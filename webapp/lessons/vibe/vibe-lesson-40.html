Phase 3: Production

Agent 生產部署：從本地開發到穩定上線的完整流程

學會在 Vercel/Cloudflare 部署 Agent 系統，並建立自動化 CI/CD 與生產監控

🚀 為什麼生產部署是 Agent 工程的最後一道關卡

在第 39 課你已經學會如何用測試框架驗證 Agent 的行為，但測試通過並不代表 Agent 可以在真實環境中穩定運作。生產部署的核心難題在於：Agent 本質上是機率性的，同樣的輸入可能產生不同的輸出，這與傳統 API 服務「同一份程式碼一定給出相同結果」的行為完全不同。你的 Agent 可能在本地 localhost 跑得很順，但部署後卻遇到模型供應商限流、超時、狀態丟失、或串接工具失敗等問題。這課要把之前學過的 Supabase、Better Auth、Redis 緩存、v0/Bolt 原型、Coding Agent 等所有技術串成一條可上線的完整流程，讓你清楚知道在 Vibe Coding 中，部署不只是一次性動作，而是建立一個讓 Agent 可以自我監控、自我恢復的機制。

1 Vercel 部署 Next.js Agent 應用程式

<span>Vercel 是目前部署 Next.js 應用程式最常見的選擇，特別適合已經用過 v0/Bolt 原型工具的開發者。部署前必須確認你的 Agent 相關的環境變數（OPENAI_API_KEY、SUPABASE_URL、SUPABASE_ANON_KEY 等）已經在 Vercel Dashboard 的 Project Settings 中設定完成，否則 Agent 在運行時會因為無法存取必要服務而拋出錯誤。部署的標準流程是：在專案根目錄建立或確認 vercel.json 存在，然後用 vercel --prod 將最新程式碼推送到生產環境。如果你的 Agent 包含 streaming（串流）功能，要特別注意 Vercel 的 Serverless 函數預設限流是 10 秒，這對於 LLM 產生大量回應時往往不夠，需要透過 maxDuration 參數延長，或在路由處理時加入 response.on('close') 來取消未完成的請求以節省資源。

2 Cloudflare Pages 部署與邊緣運算的優勢

如果你的 Agent 應用程式主要依賴 Cloudflare R2（已學過）和 Cloudflare Workers，那麼用 Cloudflare Pages 部署会比 Vercel 更順手，因為兩者同屬 Cloudflare 生態，在 wrangler.toml 中設定環境變數的方式與 Vercel 的 .env 邏輯一致但更直覺。Cloudflare Pages 特別適合需要低延遲的 Agent 應用程式，因為它的邊緣節點分佈在全球，能減少用戶端到模型的網路來回時間。需要注意的是，Cloudflare Workers 的預設執行時間上限為 30 秒（Edge Runtime），如果你的 Agent 需要更長的處理時間（例如進行多步驟 RAG 檢索），可以在路由處理函數中改用 Node.js runtime 或在 Cloudflare 的 workerd 配置中調整。另外，Cloudflare 的 Cache API 可以用來快取 Agent 的回應結果，大幅降低 LLM 呼叫成本——這是 Vercel 邊緣快取做不到的原生功能。

3 當 Vibe 破裂時的快速診斷流程

部署後最怕的是 Agent 完全無法運作，以下是<span style="color:red">Vibe 破裂</span>時的標準診斷順序：第一步，查看 Vercel 或 Cloudflare Dashboard 的 Deployment Logs，確認錯誤是否發生在部署階段（編譯失敗、環境變數遺漏）還是運行階段（API 呼叫失敗、資料庫連線超時）。第二步，如果是 API 錯誤，檢查 Supabase 的 Project Settings → API 頁面，確認 anon key 與 service_role key 的權限設定是否符合需求——很多時候部署後 DB 權限問題會被忽略。第三步，如果是 LLM 呼叫失敗，檢查環境變數中的 API Key 是否與本地開發時使用的是同一組——Vercel 的環境變數是獨立管理的，不會自動同步本地 .env.local。第四步，如果是串流（streaming）問題，在 Chrome DevTools 的 Network 面板中查看 SSE 連接是否異常中斷，並檢查伺服器端是否有 AbortSignal 超時設定。第五步，用 postman 或 curl 直接測試 Agent 的 API endpoint，排除前端渲染問題。

🔬 建立 Agent 專用的健康檢查端點
為什麼 Agent 的健康檢查比傳統 API 更複雜？

傳統 API 服務的健康檢查（/health）通常只檢查某個 endpoint 是否可存取，但 Agent 的健康檢查需要驗證三個層面：第一，LLM 模型供應商是否可達——可以用 fetch 發送一個最簡單的 /chat/completions 請求來測試，並記錄回應時間與成功率；第二，資料庫連線是否正常——用 supabase.from('health_check').select('*').limit(1) 這類最小查詢來確認；第三，外部工具（如 Stripe、Resend）的 API 認證是否有效——可以發送一個無副作用的測試請求。這三個層面中，LLM 層面最不可靠，因為模型供應商會進行限流（rate limiting）或暫時性故障，所以健康檢查應該設計成非同步輪詢，而不是同步檢查——否則每次健康檢查本身就會消耗 LLM 的 token 配額。在 Vercel 中可以用 @vercel/cron 實現自動輪詢，在 Cloudflare 中用 Cron Triggers 實現相同功能。

4 使用 Vercel 的 CI/CD 確保每次推送都經過測試

Vercel 的 Git Integration 功能讓你每次推送程式碼到 main 分支時，自動觸發測試與部署流程。要啟用這個功能，先在 package.json 中定義測試指令，例如 "test:agent" 跑你第 39 課建立的 Agent 行為測試，然後在 vercel.json 中設定 buildCommand 與 installCommand。當 GitHub Action 被觸發時，你可以用 posthog/posthog-action 來追蹤每次部署的品質指標。特別重要的一點是：Agent 的測試應該在部署前跑完，因為 Agent 行為的機率性意味著即使同一份程式碼在不同時間執行，結果也可能不同——所以測試應該專注於驗證「錯誤路徑」是否被正確處理，而不是驗證「正確輸出」。這也解釋了為什麼第 39 課要教使用測試框架（如 Vitest）來建立 Agent 的<span style="color:blue">契約測試（contract tests）</span>，而不是簡單的單元測試。

5 Agent 的生產監控：用 PostHog 追蹤每一次呼叫

第 29 課你學過 PostHog 的基礎安裝，但 Agent 的監控需要更深入。Agent 的每一次執行都可以被追蹤成一個<span style="color:purple">Trace</span>，包含以下屬性：agent_id（哪個 Agent 執行）、input_tokens（輸入了多少 token）、output_tokens（輸出了多少 token）、tool_calls</u>（執行了哪些工具）、latency_ms（總耗時）、success（是否成功）、error_message（如果失敗）。在 Next.js 中，你可以在 Agent 執行的每個階段呼叫 posthog.capture()，並在失敗時額外呼叫 posthog.capture('agent_error', { error: error.message })。這些數據可以匯入 PostHog 的 Dashboard 來建立儀表板，讓你看到「哪個 Agent 最耗費 token」、「哪個工具的失敗率最高」、「平均每次 Agent 執行需要多少時間」。這種監控讓你在 Vibe 破裂時能快速定位是<span style="color:red">前端問題、後端問題還是模型供應商問題</span>。

6 當 Vibe 破裂時：Agent 專用除錯流程

Agent 的除錯與傳統後端除錯最大的不同在於：你無法用 breakpoint 來檢查模型輸出的中間狀態。以下是 Vibe 破裂時的完整除錯流程：第一步，開啟 Vercel 或 Cloudflare 的即時日誌（Live Logs），觀察 Agent 執行的每一步。第二步，在 Agent 的每個 tool call 前後加上 console.log 或使用 next-logger 等庫來記錄呼叫內容與結果，特別關注 function_call 的參數是否正確。第三步，用 langsmith 或 langfuse 來追蹤 LLM 的完整執行軌跡——這兩個工具專門為 LLM 應用程式設計，能顯示每一輪的 input/output、所使用的 tool、消耗的 token。第四步，如果是串流問題，用 eventsource 或 fetch with streaming 的 debug mode 來看 SSE 回應是否被正確解析。第五步，用 supabase 的 Logs → SQL 頁面檢查資料庫查詢是否有異常。最後，如果所有診斷都找不到原因，嘗試<span style="color:green">降低 prompt 的複雜度</span>——很多 Agent 錯誤是 prompt 設計問題而非程式碼問題。

7 Agent 狀態管理：部署後的檢查點機制

第 35 課你學過 Agent 長任務中斷恢復工程，第 36 課學過檢查點與斷點續傳，但這些機制在<span style="color:orange">部署後的真實環境</span>中需要更嚴格的實現。當 Agent 在雲端運行時，可能有以下幾種中斷情況：Vercel Serverless 函數被重新啟動（cold start）、雲端網路斷線、模型供應商限流導致重試、使用者關閉瀏覽器頁面。為應對這些情況，Agent 的檢查點機制應該：每執行完一個 tool call 就將當前狀態寫入 Supabase（使用 upsert 操作），而不是在整個任務結束後才寫入。這樣即使 Serverless 函數被強制終止，也可以從 Supabase 中恢復到最近一次 tool call 完成時的狀態。在 Next.js 中，可以用 @supabase/ssr 套件來簡化這個過程，並確保檢查點的寫入操作使用 service_role key 而非 anon key，以避免資料庫行級安全（RLS）規則阻擋寫入。

1. 在 Vercel 部署 Agent 應用程式時，為什麼 streaming 功能特別需要注意？
  • Vercel 的預設 Serverless 函數限流是 10 秒，LLM 產生大量回應時可能超時
  • Vercel 不支援 streaming 功能，必須改用其他平台
  • Vercel 的 streaming 功能會導致所有 LLM 回應被截斷
✅ A 是正確的。Vercel 的 Serverless 函數預設有一個 10 秒的執行時間上限（maxDuration），而 LLM 產生大量 text 需要較長時間，如果不額外設定 maxDuration 參數，請求會在中途被強製作業系統終止，導致串流中斷。B 錯誤因為 Vercel 原生支援 streaming（透過 Next.js 的 NextResponse）。C 錯誤因為截斷是伺服器端的行為，不是 Vercel 的設計特性。
2. Agent 的健康檢查為什麼應該設計成非同步輪詢而非同步檢查？
  • 同步檢查會消耗不必要的 LLM token 配額，且模型供應商可能有短暫故障
  • 非同步輪詢是 Vercel 的強制要求
  • 同步檢查的速度太慢，會影響用戶體驗
✅ A 是正確的。每次 LLM 健康檢查都會消耗 token，輪詢可以控制檢查頻率，避免不必要的消耗。同時模型供應商可能有短暫故障，非同步機制可以避免健康檢查本身阻礙正常請求。B 錯誤因為 Vercel 沒有強制要求某種健康檢查方式。C 錯誤因為同步檢查的速度影響的是健康檢查本身，而非用戶體驗——用戶不會直接看到健康檢查的結果。

請依序完成以下練習

  1. 在 Vercel 上部署你的 Next.js Agent 應用程式，並在 Dashboard 的 Environment Variables 中設定所有必要的 API Key 與 Supabase 連線資訊，確認部署後 Agent 可以正常執行
  2. 建立一個 /api/health 端點，驗證 Supabase 連線與 LLM 基本可用性，並在部署後用 curl https://your-domain.vercel.app/api/health 測試健康檢查是否正常回應
