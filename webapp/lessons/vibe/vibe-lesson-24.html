API 通訊與第三方整合

讓你的 App 學會打電話——理解 API Routes、Request/Response 結構，與 Webhook 接收外部事件

1 為什麼 Vibe Coding 需要 API 通訊？

在 Vibe Coding 的脈絡裡，你的 Next.js 應用程式不應該是資訊孤島。AI Agent 負責把「靜態的 UI 與邏輯」組裝成可用的原型，但真正讓產品活起來的是它與外部世界的對話能力——讀取即時天氣、追蹤 GitHub 事件、呼叫 AI 模型、寫入資料庫，全部依賴 API 通訊。沒有這層能力，你的 Vibe 只是好看但不能用的殼。本課的核心目標是讓你能夠清楚地描述「我要叫哪一台伺服器做什麼事」，並且能看懂對方回來的結果長什麼樣子，這樣當 Vibe 破裂時你才有辦法指出問題在哪一端：是你發出去的 Request 格式錯了，還是對方的 Response 結構跟你預期不同。

2 API Routes 與 Client-Side Fetch 的差別

Next.js 提供兩種最常見的服務端通訊寫法：一是直接使用 fetch()（在 Client Component 裡調用），二是把邏輯寫進 app/api/ 目錄下的 Server Route。兩者的本質區別在於請求發生在哪一台機器上。Client-Side Fetch 的請求是從使用者的瀏覽器直接發出去，這意味著 API Key 可能會暴露在前端原始碼裡，也常常會遇到 CORS 限制。Server Route 則是由你的伺服器（localhost 或上線後的 Vercel Node runtime）發出請求，前端只負責接收結果，安全性與穩定性都更好。當 Vibe 破裂時，檢查方式很直接：打開瀏覽器的 Network 面板，看 Request 是哪一端發出的、Status Code 是多少、Response Body 的內容是否符合預期。

3 實作範例：用 Open-Meteo 免費天氣 API 寫一個 Server Route

Open-Meteo 是一個完全免費、不需要 API Key 的氣象 API，非常適合教學使用。我們先在 Next.js 專案裡新增 app/api/weather/route.ts，以下是完整的實作邏輯。這個 Route 接收使用者傳來的城市名稱（或經緯度），Proxy 到 Open-Meteo 的 API，再把結果回傳給前端。這樣寫的好處是前端永遠不會看到 Open-Meteo 的 URL，日後即使要換成需要 Key 的商業 API（例如 OpenWeatherMap），也只在本機這個 Server Route 裡改一行就好。

# 這是我們在 route.ts 裡會寫的核心 fetch 邏輯（請用 AI Agent 產生完整檔案） # 不需要手動輸入，但要看懂它在做什麼 $ cat app/api/weather/route.ts import { NextRequest, NextResponse } from "next/server" export async function GET(request: NextRequest) { const city = request.nextUrl.searchParams.get("city") ?? "台北" const geoUrl = `https://nominatim.openstreetmap.org/search?format=json&q=${encodeURIComponent(city)}` const geoRes = await fetch(geoUrl) const geoData = await geoRes.json() if (!geoData.length) { return NextResponse.json({ error: "找不到該城市" }, { status: 404 }) } const { lat, lon } = geoData[0] const weatherUrl = `https://api.open-meteo.com/v1/forecast?latitude=${lat}&longitude=${lon}&current=temperature_2m,wind_speed_10m` const weatherRes = await fetch(weatherUrl) const weatherData = await weatherRes.json() return NextResponse.json(weatherData.current) } # 啟動開發伺服器 $ bun run dev Ready at http://localhost:3000
4 Webhooks——讓外部事件主動找上門

前面學的都是「你主動去問別人拿資料」，Webhook 則是反過來：你提供一個 URL 端點，讓別的服务在發生特定事件時主動 POST 資料過來。GitHub 的 Push Event、Stripe 的付款成功通知、甚至是其他 AI Agent 完成工作後的回調，全部走這個模式。在 Next.js 裡，你只需要在 app/api/webhook/route.ts 裡寫一個 POST handler，接收 request.body 裡的事件 payload，驗證簽章（如果是 Stripe 這種有安全機制的服務），然後根據事件類型執行對應的邏輯（例如更新資料庫、發送推播）。當 Vibe 破裂時，最常見的原因是：簽章驗證失敗、content-type: application/json 沒寫對導致 request.json() 解析錯誤、或是伺服器端沒有正確返回 200 OK 讓發送端知道已經收到。

🔬 🔬 深入解析：Request 與 Response 的結構為什麼長這樣？
為什麼我們要把 request 和 response 當成結構化的物件來處理？

HTTP 通訊的本質是一問一答的契約關係。當你發送一個 Request，你同時定義了三件事：Method（GET/POST/PUT/DELETE，決定動作類型）、Headers（告訴對方你要什麼格式、身分憑證、Content-Type 是什麼）、Body（POST/PUT 時攜帶的實際資料）。而 Response 則對應地回傳：Status Code（200 成功、404 找不到、500 伺服器內部的錯誤）、Headers（Content-Type、CORS 權限、Cache-Control），以及 Body（JSON、HTML、或純文字）。理解這個對稱結構非常關鍵，因為 Vibe Coding 裡絕大部分「報錯看不懂」的問題，根源都在這裡——例如 Next.js 的 NextResponse.json() 預設會自動把 Content-Type 設為 application/json，但如果你手寫 new Response("hello") 而不指定 headers，前端收到的是純文字，不是 JSON，接著 await res.json() 就會拋出 Unexpected token 'h' 的錯誤。另一個常見陷阱：Open-Meteo 的 API 回傳的 current 欄位是一個物件，但有些人以為它會直接回傳 temperature_2m 的數值，結果在前端做 data.temperature_2m 拿到的永遠是 undefined。把 Request/Response 結構想清楚，就能精準定位這一切。

1. 在 Next.js 的 Server Route（app/api/.../route.ts）裡，以下哪一段程式碼能正確回應一個 JSON？
  • return "Hello World"
  • return new Response("Hello World")
  • return NextResponse.json({ message: "Hello World" })
✅ NextResponse.json() 是 Next.js 專屬的 Response 建構工具，它不僅回傳 JSON 格式的 Body，還會自動把 Content-Type 標頭設為 application/json，這是與一般 JavaScript new Response() 最主要的差別。選項 A 回傳的是純字串，前端收到時 Content-Type 是 text/plain，會導致 JSON.parse 失敗；選項 B 雖然不會錯，但 Content-Type 預設是 text/plain，前端若預期 JSON 也會解析錯誤。

1. 當你的 App 呼叫 Open-Meteo API 後收到 Status 200，但前端顯示「溫度：undefined」，最可能的原因是？
  • Open-Meteo API 當機了
  • API 回傳的資料結構是 { current: { temperature_2m: 25 } }，但前端直接讀取 data.temperature_2m 而沒有先取 data.current
  • 你的 Next.js 版本太舊，不支援這個 API
✅ Status 200 表示請求成功，排除伺服器端問題。Open-Meteo 的 current 是一個巢狀物件，正確的讀取路徑是 data.current.temperature_2m，若直接讀 data.temperature_2m 就會是 undefined。這不是 Next.js 版本問題，而是對 API Response 結構理解不正確所致。
