Phase 3: The Brain

多 Agent 協作

拆解複雜任務，讓多個專責 Agent 分工合作

🤖 為什麼需要多 Agent 協作？

在 Vibe Coding 中，單一 Agent 雖然強大，但當任務超出其上下文窗口或專業範圍時，就會出現「Vibe 破裂」——產出品質下降、邏輯矛盾或指令偏離。多 Agent 協作的核心在於群體智能：將複雜任務拆解為多個子任務，分配給專責 Agent，每個 Agent 專注於自己的領域，透過協作完成單一 Agent 無法獨立處理的專案。這類似現實中的軟體團隊：開發者寫程式、測試者找漏洞、架構師把關設計。在 AI 語境下，我們可以設計一個「產出 Agent」負責生成程式碼，一個「審查 Agent」負責檢查錯誤與最佳實踐，透過明確的角色分工與通訊協議，提升整體系統的可靠性與產出品質。

⚖️ 單一 Agent vs. 多 Agent 架構對比

理解多 Agent 協作的價值，需要對比單一 Agent 的局限性。單一 Agent 面對複雜任務時，容易出現上下文膨脹導致注意力分散、缺乏專業深度審查、以及難以維護長期一致性。多 Agent 架構則透過分工與專門化，解決這些問題。以下透過具體情境對比，說明兩者的差異。

2 單一 Agent 與多 Agent 情境對比

在實際開發中，我們經常遇到需要生成程式碼並同時確保品質的任務。以下是單一 Agent 與多 Agent 處理同一任務的方式對比：

單一 Agent 處理
# 單一 prompt 要求生成並審查程式碼 "幫我寫一個 Next.js 的 API 路由，處理使用者註冊，並檢查錯誤處理是否完整" # Agent 嘗試一次性完成所有步驟 # 可能導致：註冊邏輯簡陋、錯誤處理不完整、上下文過長後忽略部分要求
多 Agent 協作處理
# Agent A（產出）：專注於生成程式碼 "請生成 Next.js API 路由，處理使用者註冊，包含基礎錯誤處理" # Agent B（審查）：專注於檢查與改進 "檢查以下程式碼的錯誤處理是否完整，並提出改進建議" # 透過明確分工，每個 Agent 可專注於特定職責，提升輸出品質
🛠️ 實戰：設計雙 Agent 分工流程

實作多 Agent 協作的第一步是設計清晰的分工流程。我們以「生成並審查程式碼」為例，建立一個簡單的雙 Agent 架構。首先，定義兩個 Agent 的角色與輸入輸出。產出 Agent 接收原始需求，生成初始程式碼；審查 Agent 接收產出 Agent 的結果，進行檢查並提供反饋。接著，設計協作流程：產出 Agent 完成後，將結果傳遞給審查 Agent；審查 Agent 提供改進建議；若需要，可讓產出 Agent 根據反饋進行迭代。這個流程可以透過簡單的指令腳本或協調腳本來實現，關鍵在於明確的交接協議與輸入輸出格式。

3 雙 Agent 協作流程實作範例

以下展示如何使用 Claude Code 或類似工具，設計一個簡單的雙 Agent 協作流程。我們透過指令傳遞與輸出截斷來模擬 Agent 間的通訊。

# 步驟 1：產出 Agent 生成程式碼 $ claude -p "生成一個 Express.js 的簡單 REST API，包含 GET 和 POST 端點，使用 Express 框架" 產出 Agent 回應：生成完整的 Express 應用程式程式碼，包含 route 定義與基本錯誤處理 # 步驟 2：審查 Agent 檢查程式碼 $ cat generated_code.js | claude -p "檢查以下程式碼的潛在問題與改進建議" 審查 Agent 回應：指出缺少環境變數管理、錯誤處理不完整、缺少輸入驗證等問題 # 步驟 3：產出 Agent 根據反饋改進 $ claude -p "根據以下審查建議改進程式碼：1. 添加環境變數管理 2. 完善錯誤處理 3. 加入輸入驗證" 產出 Agent 回應：生成改進後的程式碼，包含環境變數配置、統一錯誤處理中間件、輸入驗證邏輯
🔬 多 Agent 協作的底層原理與協調機制
多 Agent 如何透過分工與通訊協議，實現超越單一 Agent 的複雜任務處理能力？

多 Agent 協作的核心在於任務拆解與專責分工。每個 Agent 可被視為一個專門的 LLM 實例，擁有不同的系統提示詞（System Prompt）與工具集，專注於特定子任務。例如，「程式碼生成 Agent」被優化為擅長結構化輸出與框架知識，「代碼審查 Agent」則被優化為熟悉最佳實踐、安全漏洞與效能瓶頸。Agent 間的通訊透過明確的介面協議實現：通常包含輸入格式（如 JSON 結構的需求描述）、輸出格式（如程式碼塊與審查報告）、以及協調邏輯（如迭代條件或最終合併規則）。這種協作模式本質上是將複雜問題分解為多個可管理的子問題，利用專項能力降低單一模型的認知負載，同時透過交叉檢查提升整體輸出品質。在 Vibe Coding 中，這種架構能有效防止「Vibe 破裂」——當單一 Agent 上下文過長或任務過複雜時，分工後的專責 Agent 能保持更高的專注度與輸出穩定性。

🩺 診斷與修復 Vibe 破裂

即使採用多 Agent 協作，仍可能出現「Vibe 破裂」——例如審查 Agent 未能正確識別關鍵錯誤、產出 Agent 忽略反饋，或協作流程中斷。診斷時，首先檢查 Agent 的輸入輸出格式是否符合預期協議；其次檢視每個 Agent 的專項提示詞是否足夠明確；最後確認協調邏輯是否有錯誤處理與迭代機制。修復策略包括：調整 Agent 的角色定義與工具集、增加明確的驗收標準、或引入第三個協調 Agent 來仲裁分歧。在實戰中，建議先記錄每個 Agent 的輸出日誌，分析破裂發生在哪个階段，再針對性地調整。

🚀 今日任務：實作多 Agent 協作流程

請依序完成以下練習

  1. 設計一個簡單的雙 Agent 協作流程，使用 Claude Code 或 Cursor 等工具，實現「程式碼生成 → 審查改進」的分工。
  2. 為產出 Agent 撰寫明確的系統提示詞，專注於生成特定類型的程式碼（例如：Express API、React 組件）。
  3. 為審查 Agent 撰寫專項提示詞，要求檢查程式碼的安全性、錯誤處理與最佳實踐。
  4. 實際執行協作流程：先讓產出 Agent 生成程式碼，再將結果交給審查 Agent，最後根據反饋進行迭代改進，並記錄每個階段的輸出與觀察到的行為變化。
