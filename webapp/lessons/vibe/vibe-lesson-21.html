Phase 3: The Brain

自動化流程（n8n）

用 n8n 串接 GitHub Actions，打造代碼提交到部署的自動化鏈

🤖 為什麼 Vibe Coding 需要自動化流程？

在 Vibe Coding 的工作流程中，我們大部分時間都花在「寫碼 → 測試 → 修復 → 部署」的循環上。當這個循環全靠人工執行時，不仅效率低落，而且最容易在「手動部署」這個環節出錯——遺漏某個步驟、設定錯誤的環境變數、或者忘記執行測試，都會導致部署失敗。n8n 作為一個開源的自動化工作流程平台，讓你能用視覺化的方式設計和執行自動化流程，特別適合用來串接 GitHub Actions 的 CI/CD 流程。它的核心價值在於：把重複性的技術決策轉化為可重複執行的流程，讓 AI Agent 不再需要記住每個部署步驟，而是透過自動化觸發器來確保每次代碼提交都能經過完整的測試和部署流程。 AI Agent 如何運用 n8n？Agent 可以透過 n8n 的 REST API 觸發或監控自動化流程，例如：當 GitHub 收到新的 push 事件時，n8n 可以自動呼叫測試 API、部署腳本，並把結果回傳給 Agent 進行異常檢測。這種「Agent 觸發 → n8n 執行 → Agent 接收結果」的模式，讓自動化流程成為 Agent 工具箱中的一個外部工具，而不需要把複雜的部署邏輯寫進 Agent 的 prompt 裡。

2 核心觀念：從手動到自動化的躍遷

在 Vibe Coding 中，自動化流程扮演著「可靠的後台執行者」角色。當 Agent 完成程式碼撰寫並提交到 GitHub 後，手動流程需要開發者自己執行測試、檢查報告、手動部署；而自動化流程則是由 GitHub Actions 接收 webhook 事件，自動觸發測試和部署，n8n 在這個過程中扮演整合者的角色——它可以把多個 Action 的結果收集起來，根據結果決定下一步動作（例如：測試失敗時發送通知、部署成功時更新監控儀表板）。 | 手動部署 | 自動化部署 | |---------|-----------| | 開發者執行測試命令 | GitHub Actions 自動觸發測試 | | 開發者檢查測試報告 | n8n 解析報告並判斷是否通過 | | 開發者執行部署命令 | 測試通過後自動觸發部署 Action | | 開發者手動通知團隊 | n8n 自動發送通知（Discord/Slack/Email） | | 情境 A：手動部署 | 情境 B：自動化部署 | |----------------|-----------------| | 提交代碼後，開發者需要： <br/>1. 執行 npm test <br/>2. 查看測試報告 <br/>3. 執行 npm run build <br/>4. 上傳到伺服器 <br/>5. 重啟服務 <br/>6. 手動通知團隊 | 提交代碼後，GitHub Actions 自動： <br/>1. 觸發測試 <br/>2. 生成報告 <br/>3. 打包應用 <br/>4. 部署到生產環境 <br/>5. n8n 接收結果並通知團隊 |

3 實戰：搭建 n8n + GitHub Actions 自動化流

首先，我們需要在本地或伺服器上部署 n8n。最簡單的方式是使用 Docker：

# 使用 Docker 部署 n8n $ docker run -it --rm \ --name n8n \ -p 5678:5678 \ -v ~/.n8n:/home/node/.n8n \ n8nio/n8n n8n ready on http://localhost:5678 👉 Open the Web UI: http://localhost:5678 # 或者使用 Docker Compose（推薦用於生產環境） $ cat > docker-compose.yml << 'EOF' version: '3.8' services: n8n: image: n8nio/n8n restart: unless-stopped ports: - "5678:5678" environment: - N8N_PORT=5678 - N8N_EDITOR_BASE_URL=http://localhost:5678 - N8N_BASIC_AUTH_ACTIVE=true - N8N_BASIC_AUTH_USER=admin - N8N_BASIC_AUTH_PASSWORD=your_secure_password volumes: - ~/.n8n:/home/node/.n8n EOF $ docker-compose up -d Created n8n_n8n_1 ... done # 驗證 n8n 是否運行中 $ curl -s http://localhost:5678/api/v1/healthz {"status":"ok"}
🔬 GitHub Actions 與 n8n 的串接原理
為什麼 n8n 適合當 GitHub Actions 的「後勤整合者」？

GitHub Actions 的本質是一個事件驅動的 CI/CD 平台，它透過 YAML 檔案定義「當某個事件發生時（如 push、pull_request），執行哪些步驟」。然而，Actions 本身的功能比較偏向「執行特定任務」，當你需要跨服務整合（例如：測試失敗時發通知、部署成功時更新資料庫）時，單靠 Actions 會變得很複雜。 n8n 的核心優勢在於它的節點系統。每個節點代表一個特定功能（HTTP 請求、數據轉換、條件判斷、通知發送等），你可以像接線一樣把節點串起來形成流程。當 GitHub 觸發 webhook 到 n8n 的 webhook 節點時，n8n 可以執行一串邏輯：先呼叫測試 API，解析返回的 JSON，根據結果決定是發送成功通知還是失敗報警，最後把結果記錄到資料庫或發送給 Slack。 這種設計讓 n8n 成為「多步驟決策流程」的理想載體，而 GitHub Actions 負責「單點任務執行」，兩者的分工非常清晰：Actions 處理測試和部署的技術細節，n8n 處理跨服務的協調和通知。對 Vibe Coding 來說，這種分工讓 AI Agent 可以專注在程式碼邏輯上，而不需要處理部署流程的複雜性。

3 實戰：建立自動化測試流程

現在我們在 n8n 中建立一個完整的自動化流程。首先開啟 n8n UI（http://localhost:5678），點擊「Create Workflow」：

# 步驟 1：在 GitHub 上建立 repository（假設已使用 Git 初始化） $ git init $ git remote add origin https://github.com/your-username/your-repo.git $ git add . $ git commit -m "Initial commit" $ git push -u origin main Enumerating objects: 10, done. Counting objects: 100% (10/10), done. Writing objects: 100% (10/10), 1.23 KiB | 1.23 MiB/s, done. Total 10 (delta 0), reused 0 (delta 0), pack-reused 0 # 步驟 2：在 GitHub 建立 .github/workflows/test.yml $ mkdir -p .github/workflows $ cat > .github/workflows/test.yml << 'EOF' name: Test and Deploy on: push: branches: [ main ] pull_request: branches: [ main ] jobs: test: runs-on: ubuntu-latest steps: - uses: actions/checkout@v4 - name: Setup Node.js uses: actions/setup-node@v4 with: node-version: '20' - name: Install dependencies run: npm ci - name: Run tests run: npm test continue-on-error: false - name: Notify n8n on success if: success() run: | curl -X POST https://your-n8n-instance.com/webhook/test-success \ -H "Content-Type: application/json" \ -d '{"repo": "${{ github.repository }}", "commit": "${{ github.sha }}"}' - name: Notify n8n on failure if: failure() run: | curl -X POST https://your-n8n-instance.com/webhook/test-failure \ -H "Content-Type: application/json" \ -d '{"repo": "${{ github.repository }}", "commit": "${{ github.sha }}", "branch": "${{ github.ref }}"}' EOF # 步驟 3：在 n8n 中建立對應的 Webhook 節點 # （此步驟在 n8n UI 中操作，這裡展示預期流程） Webhook 節點 URL: https://your-n8n-instance.com/webhook/test-success Webhook 節點 URL: https://your-n8n-instance.com/webhook/test-failure # 步驟 4：提交到 GitHub $ git add .github/workflows/test.yml $ git commit -m "Add CI/CD workflow" $ git push origin main To https://github.com/your-username/your-repo.git abc1234..def5678 main -> main
🛠️ Vibe 破裂診斷：常見問題與修復

當自動化流程「Vibe 破裂」時，通常有幾個常見原因。最常見的是Webhook 無法觸發——檢查 n8n 的 Webhook 節點是否設定為「等待請求」模式，並且確認 GitHub 的 webhook URL 是否正確。另一個常見問題是測試失敗但流程繼續，這通常是因为 GitHub Actions 的 continue-on-error: true 設定錯誤，或者 n8n 的條件判斷邏輯有問題。 第三個常見問題是部署失敗，這通常與環境變數或憑證有關。確保你在 n8n 中使用「憑證」功能來管理 API keys 和密碼，不要直接在流程中硬編碼敏感資訊。第四個問題是通知延遲或丟失，這可能是因為 n8n 的執行佇列過長，或者 webhook 節點的超時時間太短。 當問題發生時，按以下順序診斷：1）檢查 GitHub Actions 日誌（Repository → Actions → 選擇最近的 workflow run），2）檢查 n8n 的執行歷史（左侧選單 → Execution），3）手動觸發 webhook 測試（在 n8n 中點擊 Webhook 節點的「Test webhook」按鈕），4）查看 n8n 日誌（如果開啟了日誌記錄）。

✏️ 小測驗

請先回答，再點擊「查看答案」

1. 在 n8n 中，Webhook 節點的哪種模式最適合用來接收 GitHub 的 push 事件？
  • 等待模式（Wait）
  • 立即回應模式（Immediate）
  • 佇列模式（Queue）
✅ 立即回應模式會直接處理請求並返回響應，適合 GitHub webhook 這種「需要立即確認收到」的場景。等待模式會讓 Webhook 暫停流程等待後續資料，適合需要分階段收到的場景。佇列模式用於高負載情況。
2. 當 GitHub Actions 的測試失敗時，n8n 收到通知後應該做什麼？
  • 自動修復測試代碼並重新提交
  • 發送失敗通知給開發者，並記錄失敗詳情
  • 忽略失敗，繼續執行部署
✅ n8n 的角色是整合者和協調者，不應該擅自修改代碼。正確做法是發送通知讓開發者知道問題，並記錄詳細資訊供後續除錯。自動修復代碼超出了 n8n 的能力範圍，而忽略失敗則會導致問題積累。
3. 以下哪個是 n8n 相對於純 GitHub Actions 方案的優勢？
  • n8n 可以編譯程式碼
  • n8n 提供視覺化流程編輯和跨服務整合能力
  • n8n 可以直接執行 JavaScript 代碼
✅ n8n 的核心價值在於視覺化流程編輯和跨服務整合。雖然 GitHub Actions 也能執行 JavaScript，但 n8n 的節點系統讓複雜的跨服務流程更容易設計和維護。編譯程式碼不是 n8n 的功能，而執行 JavaScript 在兩者中都能實現。
