Phase 3: The Brain

工具設計與 Function Calling

讓模型不只是說話，而是能做實事

🧰 為什麼 Agent 需要工具？

在之前的課程我們學過 Agent 的核心公式 Agent = LLM + 上下文 + 工具，這裡的「工具」就是讓 AI 從純粹的文字產生器，變成能與外部世界互動的實體。沒有工具，模型只能讀懂你給它的歷史對話，然後輸出文字；有了工具，它就能讀取檔案、執行命令、查詢資料庫、呼叫 API。Vibe Coding 的本質就是：你描述意圖，AI 決定用哪些工具來完成。當 Vibe 破裂時，最常發生的情況之一就是 AI 根本不知道該用哪個工具，或者用它選錯工具——例如你想讓它查某個環境變數，它卻跑去編輯檔案。理解工具的設計邏輯，是診斷這類問題的第一步。

🔌 Function Calling 是什麼？

Function Calling（或稱 Tool Use）是 LLM 支援的一種輸出格式：當模型的回應需要外部資料或動作時，它不會直接輸出文字，而是產出一個結構化的 JSON 物件，宣告「我要呼叫某個工具，傳入這些參數」。這個 JSON 會回到你的程式碼，由你執行真正的函式，再把結果送回給模型。整個流程是：使用者提問 → 模型輸出 tool_call → 你的程式碼執行 → 回傳 tool_result → 模型繼續生成文字回應。這個機制讓模型的能力突破訓練資料的界限，因為你可以在程式碼層面插入任意邏輯。Vibe Coding 中常用的框架（如 Vercel AI SDK、LangChain、MCP）都是圍繞這個概念建立抽象層。

🎯 AI 如何選擇工具與決定參數

模型面對一組工具定義時，會根據當下的上下文（歷史對話、系統提示詞、工具描述文字）來做兩件事：第一，選出應該呼叫哪一個工具；第二，為該工具填入參數。選擇過程本質上是一個分類任務——模型把每個工具的 description 字段與使用者意圖做比對，選出最相關的。參數填充則是更困難的部分：模型需要從對話中提取出正確的型別、位置、預設值。如果工具描述寫得不清楚，或參數名稱與使用者表達方式差距太大，模型就容易選錯或傳入錯誤資料。因此，工具描述的品質直接決定了 AI 的準確度。這也是為什麼在 Vibe Coding 中，「如何描述工具」是一門關鍵技術。

2 工具的兩個層級：定義 vs 執行

理解工具的設計，必須先把「定義」與「執行」拆開。定義是給模型看的——告訴它這個工具叫什麼、能做什麼、需要哪些參數；執行是給你程式碼看的——真正去讀檔案、跑命令、呼叫 API。兩者的責任完全分開：模型只負責決定要叫什麼、傳什麼，程式碼只負責照做。

工具定義（給模型看）
{ "name": "get_env_var", "description": "取得環境變數的值，用於除錯或驗證設定", "parameters": { "type": "object", "properties": { "varName": { "type": "string", "description": "環境變數名稱" } }, "required": ["varName"] } }
工具執行（給程式碼看）
async function get_env_var(varName) { return process.env[varName] ?? "UNSET"; }
3 實作：用 Vercel AI SDK 定義工具

以下是一個使用 Vercel AI SDK 定義工具的真實範例。這個工具允許模型讀取當前目錄下的 .env 檔案，並回傳指定變數的值。你會注意到工具的描述非常具體，這會幫助模型在需要除錯環境設定時準確選擇它。

# 先確認你有安裝 ai 套件 $ npm install ai # 工具定義範例（放在你的 API Route 或 Agent 邏輯中） const tools = { get_env_var: { description: "讀取 .env 檔案中的環境變數值，用於除錯部署設定或驗證變數是否已存在", parameters: z.object({ varName: z.string().describe("要查詢的環境變數名稱，例如 DATABASE_URL"), }), execute: async ({ varName }) => { const dotenv = await import("dotenv"); dotenv.config(); return process.env[varName] ?? "NOT_FOUND"; }, }, }; # 在 Next.js App Router 的 Route Handler 中使用 # app/api/chat/route.ts export async function POST(req: Request) { const { messages } = await req.json(); const result = await streamText({ model: openai("gpt-4o"), messages, tools, maxSteps: 5, }); return result.toDataStreamResponse(); }
👁️ 觀察一次完整的 Tool Call 流程

要真正理解 AI 怎麼選擇工具，最好的方式就是親眼觀察一次完整的呼叫過程。當你使用 Claude Code、Cursor Agent 或任何支援 Tool Use 的框架時，模型的每一次 tool_call 都會產生一個結構化的請求。你可以在開發者工具中看到这个 JSON，內容包含 tool name、arguments、以及 tool call ID。這個觀察過程非常實際：當 Vibe 破裂（例如模型做出錯誤決策）時，你能直接看到它選了哪個工具、傳了什麼參數，從而判斷是工具描述不夠清楚、參數型別不符，還是上下文資訊不足導致模型誤判。

為什麼模型有時會「幻覺」出根本不存在參數？

這是一個常見的 Vibe 破裂原因。當工具的 parameters schema 沒有完整定義 required 欄位，或某個參數的 description 寫得太模糊時，模型會根據語境猜測參數內容。例如你定義了一個 query_issues 工具，參數是 query: string，模型可能會從對話中提取出像是 "show all" 這種不完整的字串，因為它沒有被告知這個字串應該是什麼格式。更嚴重的情況是，模型會直接編造參數，這就是所謂的 hallucination。解決方案是：把參數的 description 寫得像給一個完全不懂你專案的開發者看，並在執行函式中加入參數驗證（例如 zod schema 檢查），讓錯誤在執行階段就被攔截，而不是讓模型在不知道的情況下繼續運作。

🔍 診斷 Vibe 破裂：工具相關的常見故障

當 Vibe 破裂時，與工具相關的故障可以分為幾類。第一類是「模型根本沒選工具」——可能因為工具描述太不重要，模型認為不需要；或是 maxSteps 設得太低，模型來不及呼叫。第二類是「模型選了錯誤工具」——通常來自描述重疊，兩個工具看起來能做同一件事。第三類是「參數傳錯了」——型別不符、必填欄位遺漏、或值不符合預期格式。第四類是「執行時失敗」——工具定義正確，但執行函式拋出例外，這時模型通常會收到錯誤訊息並嘗試重試或換工具。診斷時請先檢查模型實際輸出的 tool_call JSON，再看執行結果，最後檢查工具描述是否足夠明確。

工具描述模糊導致誤選
{ "name": "search_code", "description": "搜尋程式碼", "parameters": { "query": "string" } } # 問題：「搜尋程式碼」太泛，模型可能會把它和 grep、find、或 even 讀檔案混淆
工具描述明確區分用途
{ "name": "grep_source_code", "description": "使用 ripgrep 在 src/ 目錄下搜尋程式碼關鍵字，僅用於查找特定函式或變數的使用位置。不適用於讀取整個檔案內容（應使用 read_file）。", "parameters": { "query": { "type": "string", "description": "要搜尋的關鍵字或正規表達式，應為短語而非完整句子" } } }
⚡ 工具設計的三個黃金法則

基於前述的故障模式，工具設計可以歸納成三條法則。第一，描述要比功能多說一半：不要只寫「做什麼」，要寫「在什麼情境下用、不要用來做什麼、參數應該長得像什麼樣」。第二，參數驗證放在執行階段：不要在定義時就依賴模型不犯錯，用 zod 或同類庫在函式內再次檢查，並回傳明確的錯誤訊息讓模型知道哪裡錯了。第三，讓工具之間互斥：如果兩個工具看起來能做同一件事，合併或重新命名，避免模型在兩者之間搖擺不決。這三條法則在 Vibe Coding 中特別重要，因為你的意圖是「讓 AI 自己決定怎麼做」，而工具就是它的決策空間。

✏️ 小測驗

請先回答，再點擊「查看答案」

1. 當 LLM 在 Function Calling 中「幻覺」出不存在的參數時，最可能的根本原因是什麼？
  • 模型的訓練資料不足
  • 工具的 parameters schema 缺少 required 欄位或 description 不夠明確
  • 執行函式的程式碼有 bug
✅ 選項 B 正確，因為當參數描述模糊或缺少 required 標記時，模型會根據上下文猜測參數內容，容易產生不存在的參數。選項 A 錯誤——幻覺不是訓練資料問題，而是 schema 設計問題。選項 C 錯誤——執行函式的 bug 不會導致模型輸出錯誤參數，它只會在參數被傳入後才發生。
2. 以下哪一種工具描述最能幫助模型正確選擇工具，避免與相似工具混淆？
  • "讀取檔案內容"
  • "使用 cat 命令讀取指定路徑的純文字檔案，適合快速查看配置或小檔案。不適合讀取大型二進位檔或需要解析的 JSON（應使用 read_json_file）。"
  • "讀取檔案"
✅ 選項 B 正確，因為它明確說明了工具的適用情境、不適用情境，以及與其他工具的區分方式，能有效減少模型誤選。選項 A 和 C 都過於簡略，沒有提供任何排除條件或對比資訊，模型容易在多個相似工具之間做出錯誤判斷。
3. 在 Vercel AI SDK 中，maxSteps 設為 1 會造成什麼問題？
  • 模型只能呼叫一個工具，之後就停止回應
  • 工具呼叫會失敗並拋出錯誤
  • 模型無法輸出任何文字
✅ 選項 A 正確，因為 maxSteps=1 表示模型在產生一次 tool_call 後就結束多步驟推理，無法根據工具結果繼續決策。這在某些需要多步工具調用的場景中會導致 Vibe 破裂。選項 B 和 C 都錯誤——maxSteps 限制的是推理步數，不是工具執行的成功與否。
🚀 今日任務

請依序完成以下練習

  1. 任務一：建立一個簡單的本地環境查詢工具。在你的 Next.js 專案中，用 Vercel AI SDK 定義一個 get_env_var 工具，描述要寫清楚適用情境與參數格式，並在執行函式中用 zod 驗證輸入。
  2. 任務二：用 Claude Code 或 Cursor Agent 與你的工具互動。讓模型呼叫 get_env_var 查詢 NEXT_PUBLIC_APP_NAME，觀察工具選取過程，並記錄模型輸出的 tool_call JSON 內容。
  3. 任務三：故意寫一個模糊的工具描述（例如只寫「搜尋」），然後對比寫一個明確的描述（說明用途、限制、參數格式），實際觀察模型在這兩種描述下選取行為的差異，並記錄在哪種情況下模型更容易選錯工具。
  4. 任務四：如果模型執行了工具卻回傳了錯誤，試著在工具執行函式中故意拋出一個錯誤訊息，觀察模型接著會如何回應——它會重試、換工具，還是直接放棄？這是診斷 Vibe 破裂時最有用的觀察方法。
