Phase 3: The Brain

AI Agents 對比

在終端機與 IDE 之間，找出適合不同開發情境的 Agent 武器

🧠 為什麼需要 Agent 選擇能力？

在 Vibe Coding 的實踐中，我們已經熟練使用 Cursor 來快速迭代 UI、用 v0 做原型，但當專案進入更複雜的階段——例如需要讀取整個程式碼庫、執行測試、修復跨檔案的 bug，或者部署到伺服器——單純在 IDE 裡面打字已經不夠了。這就是「Brain」階段要解決的問題：認識不同的 AI Agent 工具，並且知道在什麼情境下該用哪一種。 Claude Code 是一個跑在終端機（Terminal）裡面的 Coding Agent，它能直接操作你的檔案系統、執行 bash 指令、讀取 repository，適合處理需要大量背景作業、測試驗證、Git 操作的任務。Cursor 則是內建在編輯器裡的 Agent，適合邊看程式碼邊修改、快速原型、UI 迭代這類需要視覺回饋的任務。理解這兩者的差異，不是為了選邊站，而是為了在 Vibe 破裂時能準確判斷：問題該交給誰來解決。

🔄 Claude Code 與 Cursor 的核心差異

這兩個工具的差異可以歸納成一個公式：Claude Code = LLM + Shell + 檔案系統權限，而 Cursor = LLM + IDE Context + 即時視覺回饋。Claude Code 由 Anthropic 開發，預設使用 Claude 模型，它在終端機中運作，擁有完整的 shell 權限——可以執行 git、npm test、docker 等指令，甚至能讀取整個專案的檔案結構來理解上下文。它擅長的是「需要動手做」的任務：重構、部署腳本、批量修改、自動化流程。Cursor 的優勢在於「需要觀察」的任務：即時預覽組件樣式、對比修改前後的外觀、在複雜 UI 結構中快速定位問題。當你的 Vibe 是「我想看到畫面變化」，用 Cursor；當你的 Vibe 是「我想要跑這套測試然後確定沒有 regression」，用 Claude Code。

⚖️ 情境對照：什麼時候用哪個？

選擇正確的 Agent 能節省大量時間，而選錯則會導致無謂的來回。以下列出三個典型情境，看看兩個 Agent 各自的行為方式有何不同。

2 情境對照（續）

下面是同一個任務在不同 Agent 中的運作方式對比，請特別注意權限範圍和上下文來源的差異：

Claude Code（終端機 Agent）
$ claude > "幫我修好這個 bug：在 src/utils.ts 第 42 行有一個 type error，然後跑測試確認修復成功" # Claude Code 會先讀取檔案內容 # 然後執行 `npm test` 或對應的測試指令 # 修復後自動驗證，過程全在終端機中完成 # 你可以看到完整的 git diff 和測試輸出
Cursor（IDE Agent）
# 在 Cursor 編輯器中開啟 src/utils.ts > 使用 Cursor Composer 或 Chat 功能輸入同樣指令 # Cursor 會讀取當前打開的檔案上下文 # 可以直接在編輯器中看到修改建議並單擊接受 # 但無法直接執行測試指令來驗證 # 測試驗證需要手動切到終端機執行
3 指令實戰：啟動與基本操作

Claude Code 的啟動方式非常簡單，但在正式使用之前，需要先完成安裝並理解它的幾個核心指令。下面是從安裝到執行第一個任務的完整流程。

🔬 深入解析：Agent 架構與上下文工程
為什麼同樣的指令，Claude Code 和 Cursor 給出不同質量的答案？

這背後的核心原理是「上下文」（Context）的來源與規模不同。根據 Agent 的基本公式：Agent = LLM + Context + Tools，兩個工具使用的是相近的 LLM（Claude 模型），但 Context 和 Tools 的範圍天差地遠。Claude Code 的上下文可以包含整個 repository 的檔案結構——它能執行 grep、讀取多個相關檔案、甚至運行 git log 來理解歷史變更。這意味著它的「情境感知」是橫向的，能夠理解跨檔案的依賴關係。Cursor 的上下文則來自 IDE：當前打開的檔案、選取的程式碼區塊、以及你手動加入的補充說明。它的感知是縱向的，深入但範圍有限。當 Vibe 破裂時，如果你發現 Agent 給了錯誤的修復建議，首要檢查的就是上下文是否足夠——Claude Code 可能需要你明確告知要處理哪些檔案，Cursor 則需要你打開正確的檔案並選取相關程式碼。這也是為什麼 Context Engineering（上下文工程）成為 Agent 時代最重要的技能之一：你如何組織和提供上下文，直接決定了 Agent 能否正確理解問題。

🛠️ Vibe 破裂診斷：Agent 行為異常的常見原因

當 AI Agent 給出錯誤建議、忽略關鍵檔案、或者執行結果與預期不符時，這不是 Agent「壞了」，而是上下文或工具配置出現了問題。在 Vibe Coding 中，學會診斷這種狀況比學會使用指令更重要。第一個常見原因是上下文不足——Agent 看不到完整的情境。例如，用 Claude Code 修復一個依賴外部庫的 bug，但沒有告知它相關的型別定義在哪裡，它就可能做出錯誤假設。第二個原因是工具權限設定不合適——Claude Code 預設會詢問你允許它執行哪些指令，如果你過度限制，它可能連基本的 npm install 都無法執行，導致任務卡住。第三個原因是 prompt 不夠明確——Agent 擅長處理結構化指令，如果你只說「修好它」而不說明具體症狀、錯誤訊息或預期行為，它會根據不完整的資訊做猜測，結果往往偏離你的期望。診斷時，建議先檢查 Agent 讀取了哪些檔案、執行了哪些指令（Claude Code 會在對話中輸出這些資訊），然後確認你的 prompt 是否提供了足夠的約束條件。

✏️ 小測驗

請先回答，再點擊「查看答案」

1. 當你需要修復一個跨越多個檔案的 TypeScript 型別錯誤，並執行整組測試來驗證修復結果時，以下哪種 Agent 配置最有效？
  • 在 Cursor 中打開所有相關檔案，使用 Chat 功能要求修復，然後手動切換到終端機執行測試
  • 使用 Claude Code，直接給出完整的錯誤訊息和相關檔案路徑，讓它自動讀取檔案、修復並執行測試
  • 在 Cursor 中使用 Composer 功能，因為它能同時看到所有打開的檔案
✅ 選項 B 正確，因為 Claude Code 作為終端機 Agent，擁有完整的檔案系統和 shell 權限，能夠主動讀取多個檔案、理解跨檔案依賴、並直接執行測試指令來驗證結果，形成一個完整的「讀取→修改→驗證」閉環。選項 A 的问题是需要在兩個工具之間手動切換，工作流程斷裂，容易遺漏步驟。選項 C 看似合理，但 Cursor 的 Context 範圍取決於實際打開的檔案，並非所有相關檔案都會自動包含在上下文中，而且 Cursor 無法直接執行測試指令，仍需手動操作。
2. 關於 Context Engineering 在 Vibe Coding 中的角色，以下哪項描述最準確？
  • Context Engineering 是指使用更大的模型來獲得更好的理解，因為上下文長度沒有限制
  • Context Engineering 是指精心組織和提供給 Agent 的資訊結構，包括檔案路徑、錯誤訊息、依賴關係等，以確保 Agent 能正確理解問題並做出合適行動
  • Context Engineering 是 Agent 內部的自動優化機制，開發者不需要主動參與
✅ 選項 B 正確，Context Engineering 的本質是「開發者如何有策略地組織上下文資訊來引導 Agent 的行為」。這包括提供清晰的錯誤訊息、相關的檔案路徑、必要的背景說明，以及明確的任務目標。選項 A 錯誤，因為即使是最先進的模型也有上下文長度限制（例如 Claude 的上下文視窗通常為 200K token），不可能無限擴大。選項 C 錯誤，因為 Context Engineering 主要依賴開發者的主動行為——你決定給 Agent 看什麼、怎麼描述問題——這不是 Agent 內部的自動機制，而是人機協作中最重要的技能之一。
🚀 今日任務

請依序完成以下練習

  1. 在一個現有的 Next.js 專案中，用 Cursor 的 Chat 功能修復一個 UI 層級的 bug（例如按鈕樣式錯誤或排版問題），觀察它如何讀取上下文並給出修改建議，記錄它讀取了哪些檔案
  2. 安裝 Claude Code（npm install -g @anthropic-ai/claude-code 或依官方文件操作），在終端機中啟動它，給它一個需要讀取多個檔案的修復任務（例如：修復一個來自外部 API 的資料處理邏輯錯誤），觀察它執行的完整過程，特別是它讀取了哪些檔案和執行了哪些指令
  3. 設計同一個跨檔案 bug 修復任務，分別用 Claude Code 和 Cursor 執行，記錄兩個 Agent 在上下文感知範圍、執行步驟、以及最終結果上的差異，重點比較「測試驗證」環節兩者的行為
  4. 當某個 Agent 給出明顯錯誤的修復建議時，嘗試用 Context Engineering 的方式改善 prompt——加入更具體的錯誤訊息、相關檔案路徑、以及你已經嘗試過的修復方案，再次執行任務，觀察改善效果，並總結什麼樣的上下文結構最有效
