Phase 3: Production-Grade Agent

Agent 長任務中斷恢復工程

用 Checkpoint 與 State Machine 讓 Vibe 不再因為一次失敗就全盤崩解

1 為什麼長任務恢復是 Vibe Coding 的基礎設施

在 Vibe Coding 的實踐裡，我們期待 AI Agent 能一次執行多個步驟、完成複雜的協作流程。然而，任何一個步驟因為網路超時、API 限流、token 用量超標或沙盒安全規則觸發而失敗，就會讓整個任務狀態丟失，開發者必須從頭開始重新觸發，這正是 vibe 破裂 最常見的情境之一。長任務中斷恢復（Long-Task Resumption）透過在關鍵節點保存 Agent 的狀態快照（Checkpoint），讓系統在失敗後能夠從最後一個已完成的步驟繼續執行，而不是重複已經完成的動作。它同時也是一種 成本控制 的手段：每次中斷後不需要重新產生相同的上下文與工具呼叫結果，就能直接推進後續步驟。實務上，Agent 會在執行完一個原子性步驟後，將當前的 state、message_history、tool_results 與 next_action 寫入外部儲存（例如 Redis、Supabase 或本地檔案），並在啟動時檢查是否存在未完成的執行序，若存在就載入並繼續。Vibe 破裂時的診斷首先應確認是否存在有效的 Checkpoint 記錄，其次檢視該記錄的時間戳記與步驟 ID，接著檢查外部儲存服務是否可正常存取，最後模擬從該狀態繼續執行，觀察 Agent 是否會重複呼叫已成功的工具或是否進入無限循環。

2 狀態機 vs 無狀態重試

設計長任務恢復時，最常見的兩種架構選擇是 無狀態重試（Stateless Retry）與 有狀態狀態機（Stateful State Machine）。前者在步驟失敗後直接重新執行整個 Agent 流程，缺點是會重複產生相同的上下文與工具呼叫，不僅增加 token 成本，也可能因為外部服務的冪等性問題而產生副作用。後者則透過明確的狀態轉換圖來管理執行進度，只有失敗的狀態需要中斷恢復。無狀態重試適合步驟數少、外部依賴冪等性明確且失敗率極低的場景；有狀態狀態機則適合步驟數多、步驟之間有依賴關係、或外部服務非冪等（例如建立資源、發送通知）的複雜流程。當 Vibe 破裂時，若發現錯誤訊息提示「重複執行相同動作」或「重複呼叫同一 API」，通常表示當前架構是無狀態重試，需要導入狀態機來避免資源浪費。

3 實作 Checkpoint 的三個關鍵層級

實作長任務恢復系統時，需要處理三個層級的狀態儲存：執行序層（Execution Layer）負責決定下一個要執行的步驟，通常透過狀態欄位（如 current_step 或 status）來追蹤進度；上下文層（Context Layer）負責儲存當前的訊息歷史與工具結果，讓 Agent 在恢復時能維持完整的對話上下文，避免重新產生相同內容；工具層（Tool Layer）負責記錄每個工具的呼叫結果，以便在恢復時跳過已成功的步驟，直接載入先前結果。這三個層級必須協調一致，才能避免狀態不一致的問題。例如，若只儲存了上下文但沒有儲存工具結果，恢復後 Agent 可能會因為看不到工具輸出而重複呼叫工具；若只儲存了工具結果但沒有儲存上下文，Agent 可能會因為失去對話脈絡而產生脫節的回應。

🔬 深入解析：為什麼 Checkpoint 不能只存「下一步該做什麼」
只記下一個「步驟編號」真的足夠嗎？

Checkpoint 的儲存內容決定了恢復時的準確性與效率。許多初學者會犯下只儲存 current_step 的錯誤，認為只要記住下一步該做什麼就足夠。然而，這種做法忽略了 Agent 恢復後需要完整的上下文才能正確執行後續步驟。當 Agent 從步驟 2 恢復時，它需要知道步驟 1 已經成功執行了什麼、收到了什麼工具結果、以及當前的對話脈絡為何。如果只記錄步驟編號，Agent 在恢復後可能會因為缺乏上下文而重新產生步驟 1 的輸入，導致工具被重複呼叫，或者因為不知道步驟 1 的結果而做出錯誤的判斷。此外，工具呼叫通常具有副作用（例如建立資料庫記錄、發送郵件），重複執行可能產生重複資源或通知。因此，一個完整的 Checkpoint 必須包含 當前的完整訊息歷史、已執行事務的工具結果、任務的狀態標記（如 pending、completed、failed）以及 錯誤追蹤資訊（如失敗時間、錯誤訊息）。這樣才能確保恢復後的 Agent 能在完全一致的環境中繼續執行，而不是重新開始或做出錯誤的假設。

請依序完成以下練習

  1. 使用 Supabase 或 Redis 實作一個簡單的 Agent Checkpoint 儲存機制，讓 Agent 在執行完每個步驟後能將狀態寫入資料庫。
