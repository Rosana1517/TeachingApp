Phase 2: Agent Engineering

第 34 課：Agent 沙盒安全

讓 Vibe Coding 的 AI Agent 安全執行系統操作，同時避免災難性錯誤

🛡️ 為什麼沙盒是 Vibe Coding 的守門員

在 Vibe Coding 的工作流中，AI Agent 經常被賦予執行檔案操作、安裝套件、甚至啟動伺服器的權限。這些能力讓 Agent 能快速實現開發者的意圖，但同時也是一把雙面刃。Agent 沙盒安全的核心目標是：讓 Agent 能在一個受限、可預測的環境中執行操作，同時守住系統底線，避免因為提示詞誤導、上下文污染或模型失誤，導致刪除重要檔案、寫入錯誤權限、或竄改生產環境資料。 沙盒的架構通常包含三個層面：權限最小化（Agent 只能存取必要的檔案路徑與指令）、指令白名單（限制可執行的命令類型，例如禁止 rm -rf /）、以及執行結果預覽（讓開發者在 Agent 實際執行前，先看到擬執行指令的摘要）。在 Vibe Coding 中，沙盒不是要阻止 Agent 做什麼，而是讓 Agent 知道「在這個專案範圍內，你可以安全地做這些事」，這樣你才能在保持快速迭代的同時，不會因為一次誤操作而重啟整個專案。 當 Vibe 破裂時，很多時候是因為 Agent 執行了預期外的指令，或者因為權限設定過於寬鬆導致系統狀態失穩。透過沙盒機制，你可以在發生問題前先截獲可疑行為，並即時回滾或修正。

⚙️ AI Agent 如何調用沙盒工具

在實作層面，AI Agent 調用沙盒主要透過兩種方式：Function Calling（工具定義）與命令執行中介層。當你使用 Claude Code、Cursor 或自建 Agent 時，你可以定義一組工具函數，例如 read_file(path)、write_file(path, content)、run_command(cmd, args)。這些工具函數內部會串接沙盒邏輯：檢查 path 是否在允許的目錄範圍內、檢查 cmd 是否在白名單中、以及記錄每次執行的上下文以便事後審查。 當 Vibe 穩定時，Agent 會順暢地呼叫這些工具，並在執行完後回傳結果。但如果你在提示詞中沒有明確設定沙盒規則，Agent 可能會依賴模型的內建知識來決定哪些操作是「安全的」，這往往不可靠。因此，最佳實踐是在工具定義層面就嵌入安全檢查，而不是依賴模型自行判斷。例如，你可以在 run_command 中加入預設的拒絕對照表，包含 rm -rf、drop database、sudo 等高风险指令，這樣即使提示詞被污染，Agent 也無法繞過這些限制。

🔧 沙盒實戰設定範例

以下是一個簡單的沙盒工具函數實例，展示如何在 Node.js 環境中限制 Agent 只能執行特定的命令集，並檢查檔案路徑是否在專案根目錄內。這段程式碼可以整合進你的 Agent 工具層，作為 Vibe Coding 工作流的基礎安全防護。 首先，我們定義一個 SAFE_COMMANDS 列表，僅允許 npm、git、ls、cat、mkdir、cp、mv 等常用指令。接著，在執行任何命令前，會檢查命令前綴是否在白名單中，如果不是，直接拒絕。對於檔案操作，則會將路徑解析為絕對路徑，並確認其位於 process.cwd() 之下，避免 Agent 意外存取系統目錄或使用者家目錄。 這種設計讓 Vibe Coding 的流程既保持彈性，又守住底線。當 Vibe 破裂時，你可以檢查日誌中是否有被攔截的指令，快速定位是哪個步驟觸發了安全規則。

🔬 深入解析：為什麼沙盒不能只靠模型內建知識
為什麼依賴 LLM 自行判斷安全邊界是不可靠的？

大型語言模型雖然能理解「安全」這個抽象概念，但它們的訓練資料並未針對「特定專案的系統權限結構」進行最佳化。當 Agent 被賦予執行命令的權限時，模型會基於一般性的安全知識來推斷哪些操作「應該」是被允許的，但這種推斷充滿了不確定性。例如，模型可能認為 rm -rf /tmp/* 是安全的，因為路徑在 /tmp 下，但它無法知道你的 Agent 是否正在某個時間敏感的 CI/CD 流程中，而 /tmp 裡可能有正在執行的腳本暫存檔。 此外，提示詞工程中的上下文污染問題會進一步放大風險。如果對話歷史中出現了被惡意或意外引入的指令，模型可能在後續回覆中無意間複述或放大這些指令的影響範圍。沙盒機制的作用，就是在模型層面之下建立一道硬性的執行閘門，讓即使模型「以為」某個操作是安全的，實際上也會被工具層攔截。這種「defense in depth」的設計，才是 Vibe Coding 能長期穩定運作的關鍵。

✏️ 小測驗

請先回答，再點擊「查看答案」

1. 以下哪一項是 Agent 沙盒安全的主要目的？
  • 讓 Agent 能夠執行任意指令以加速開發
  • 在限制範圍內讓 Agent 安全執行操作，避免災難性錯誤
  • 完全取代模型的安全判斷能力
✅ 選項 B 正確，因為沙盒的目標不是阻止 Agent 做事，而是在可控範圍內授權，避免誤操作導致專案或系統受損。選項 A 錯誤，因為允許任意指令會失去安全控制。選項 C 錯誤，沙盒是輔助而非取代模型判斷，兩者協同才能兼顧彈性與安全。
2. 當 Vibe 破裂時，如何快速定位是否為沙盒攔截所致？
  • 檢查 Model 的內部權重分佈
  • 查看 Agent 工具的執行日誌，尋找被拒絕對照表攔截的指令
  • 重新開機伺服器後重試
✅ 選項 B 正確，因為沙盒機制會在工具層記錄每次執行的結果，包含被攔截的指令與原因。選項 A 錯誤，模型內部權重無法直接反映執行時的安全攔截。選項 C 錯誤，重新開機無法解決安全規則的問題。
🚀 今日任務

請依序完成以下練習

  1. 在你的 Next.js 專案中建立一個 sandbox.ts 工具檔案，實作 run_command 函數，包含命令白名單與路徑檢查邏輯。
  2. 使用 Claude Code 或 Cursor 創建一個新對話，嘗試讓 Agent 執行 rm -rf / 或 sudo apt update，觀察沙盒工具是否成功攔截，並記錄下來的錯誤訊息。
  3. 將沙盒工具整合進你的 Agent 工具列表，確保只有 npm、git、ls、cat 等指令可執行，並測試 Agent 是否能正常完成檔案讀寫與命令執行。
  4. 模擬一次「Vibe 破裂」情境：在提示詞中加入一段誤導性的上下文，觀察 Agent 是否仍會嘗試執行受限指令，並記錄沙盒的攔截反應。
