第 42 課：多 Agent 通訊協議與同步原語

讓多個 AI Agent 安全對話的通訊機制與鎖工程

1 Vibe Coding 中的多 Agent 通訊角色

在多 Agent 協作環境裡，通訊協議（Communication Protocol）決定了 Agent 之間如何傳遞任務、交換上下文與同步執行狀態。Vibe Coding 強調「順暢的創作流程」，當多個 Agent 同時運作時，若通訊設計不佳，就會出現訊息遺失、重複執行、執行序錯亂等問題，直接導致 Vibe 破裂。本課會介紹基於事件與訊息佇列的通訊模式，讓你理解 Agent 如何透過 Redis Streams 或 BullMQ 這類可靠佇列進行非同步對話，同時也能處理同步場景下的共享資源競爭。

2 Agent 如何調用通訊協議

AI Agent 通常透過 Orchestrator（協調器）模式來調用通訊協議：協調器會建立一個訊息通道（例如 Redis Stream），各個 Worker Agent 訂閱或發布訊息。當主 Agent 需要分派任務時，它會將任務封裝成 JSON 並推入佇列，worker Agent 輪詢或收到通知後消費訊息，處理完畢再回傳結果。這種設計讓每個 Agent 保持無狀態、可水平擴展，同時避免了直接 HTTP 呼叫 帶來的耦合與超時問題。在 Vibe Coding 中，這種非同步通訊讓多個 Agent 能「同時工作而不互相阻擋」，保持整體流暢度。

3 帶指令範例的小節

以下示範如何用 BullMQ（基於 Redis 的工作佇列）在 Node.js 中建立一個簡單的 Agent 任務通訊管道。首先安裝所需套件，接著建立工作佇列與消費者腳本。

🔬 深入解析
為什麼非同步訊息佇列比直接 HTTP 呼叫更适合多 Agent 通訊？

直接 HTTP 呼叫在多 Agent 場景中會面臨幾個致命問題：（1）耦合度高——每個 Agent 必須知道其他 Agent 的位址與 API，系統難以擴展；（2）超時與重試複雜——若目標 Agent 暫不可用，請求方需要自行處理重試邏輯，容易產生重複執行；（3）無法處理流量高峰——突發任務會直接壓垮接收端 Agent。訊息佇列（如 BullMQ）透過 ACK（確認機制） 與 失敗重試排程 解決這些問題：只有當 Worker 成功回傳結果後，訊息才會從佇列刪除，若處理過程中斷，訊息會進入 Retry Schedule 並可設定 backoff strategy（指數退避）。此外，佇列本身就是一種 負載緩衝區，能平滑處理任務尖峰，保護後端 Agent 不被瞬間大量請求擊潰。這就是為什麼在 Vibe Coding 的多 Agent 架構中，通訊協議層通常選擇非同步佇列而非同步 RPC。

4 對照小節

比較同步 HTTP 呼叫與非同步訊息佇列在多 Agent 通訊中的差異：

同步 HTTP 呼叫
// 協調器直接呼叫 Agent API const response = await fetch('http://agent-01:3000/process', { method: 'POST', body: JSON.stringify({ task: 'generate' }), timeout: 5000 }); const result = await response.json(); // 問題：超時、耦合、無法重試
非同步訊息佇列
// 協調器將任務推入佇列 await taskQueue.add('generate', { task: 'generate' }); // Worker 自動消費並處理 // 優點：解耦、自動重試、流量緩衝
5 Vibe 破裂時的診斷方法

當多 Agent 系統出現 Vibe 破裂（例如任務遺失、重複執行、死鎖）時，可按以下步驟診斷：（1）檢查佇列狀態——使用 bull-board 或 Redis CLI 查看 PENDING、WAITING、FAILED 任務數；（2）查看 Agent 日誌——確認 Worker 是否成功 ACK 訊息，若出現 Timeout 錯誤，可能是任務執行時間超過 job.timeout 設定；（3）檢查死鎖——若多個 Agent 競爭同一資源（如資料庫連線），可使用 redis-cli MONITOR 觀察命令順序，或啟用 job.delay 引入延遲避免同時競爭。Vibe 修復的關鍵是將「同步阻塞」轉換為「非同步確認」，讓每個 Agent 独立運作、透過佇列緩衝。

1. 在多 Agent 通訊中，使用 BullMQ 取代直接 HTTP 呼叫的主要優勢是什麼？
  • BullMQ 能讓 Agent 執行速度更快
  • BullMQ 提供自動重試、ACK 機制與負載緩衝，降低耦合與超時風險
  • BullMQ 不需要 Redis，可直接在記憶體中運作
✅ BullMQ 的核心優勢在於透過 Redis 提供 ACK 確認（只有成功處理才刪除訊息）、失敗重試排程（可設定指數退避），以及作為 負載緩衝區 平滑尖峰流量。選項 A 錯誤，因為佇列本身不加速執行，只是重新排程；選項 C 錯誤，BullMQ 依賴 Redis 作為持久化後端，無法完全在記憶體運作。
