Phase 3: Agent Engineering

課程主標題：AI Agent 的 Prompt 快取與成本控管

第 33 課：減少 Token 消耗、優化上下文重用的實戰技術

💰 為什麼需要 Prompt 快取？

在 Vibe Coding 環境中，我們已經讓 AI Agent 能夠自動化完成許多任務，但隨著對話輪次增加，Token 消耗會呈線性甚至指數增長。這不是理論問題——每當 Agent 重新讀取整個上下文（包含系統提示、歷史對話、工具回傳結果），你就要為每一輪重新付費。Prompt 快取（Prompt Caching）是各大 LLM API 提供的成本優化機制，OpenAI、Claude、Azure OpenAI 都支援此功能。快取的核心理念很簡單：如果連續請求之間有相同的內容，後面的請求可以大幅減低費用，因為 API 側的推理引擎可以重用已計算好的中間狀態。對 Vibe Coding 開發者而言，理解快取機制的觸發條件與限制，能直接影響 Agent 設計——例如如何安排靜態資訊的位置、如何重構提示結構，讓快命中率最大化。

🔑 快取觸發的三大條件

不同 API 提供商的快取條件略有差異，但核心原則一致。以OpenAI為例，快取觸發需要滿足三個條件：1. 相同的 model 名稱（包含版本號，例如 gpt-4o-2024-05-13，但 gpt-4o 本身不包含快取）；2. 相同的 temperature、top_p 等推理超參數；3. 連續請求的 prefix 完全相同，這通常指 system prompt 的前 N 個 token。OpenAI 的快取單位是 token，最小快取粒度為 1024 tokens，快取有效期約 5-10 分鐘。Claude（Anthropic）的快取行為更為簡單：只要同一個 conversation 內的相同內容，就會在 API 端自動快取，不需要特別參數設定，且快取粒度更細（以千 token 計）。理解這些差異後，在設計 Agent 的系統提示（System Prompt）時，就應該把不變的核心指令放在最前面，讓它成為快取的第一段內容，這樣後續對話輪次的快取命中率才會高。

🏗️ 在 Vibe Coding 中的角色

在 Vibe Coding 工作流中，AI Agent 通常是「持續對話」的模式——一個任務可能涉及數十甚至數百輪對話。每輪對話都會把當前上下文重新傳給 API，這意味著同一個系統提示会被重複發送、重複計費。Prompt 快取的作用是打破這個模式：一旦某個 prefix（例如 system prompt 或 conversation 開頭）被快取，後續請求只要共享相同的 prefix，就能以約 10% 的價格取得快取命中部分的處理權重。對 Agent 架構師而言，這代表一個設計決策：靜態資訊應該集中放在上下文的前段，而不是分散在各處。同時，快取也會影響工具回傳（tool result）的處理方式——如果工具調用結果每次都不同，它們就無法被快取，只能依賴對話歷史的重用。因此，理解快取機制能幫助你重新思考 Agent 的上下文組織方式，例如把專案規範、程式碼結構說明等不變資訊提升到 system prompt，讓快取效益最大化。

🤖 AI Agent 如何調用與控制快取

Claude Code、Claude Desktop、Cursor Agent、OpenAI Assistants API 等主流工具，底層都已自動啟用快取功能，你不需要手動設定。但作為 Vibe Coding 的進階使用者，你應該知道如何設計提示來主動利用快取。首先，確保每次對話的開頭內容一致——例如相同的 system prompt、相同的 tool definitions。其次，避免在每次請求中變動 prefix，比如在 system prompt 中加入時間戳記、動態 ID，這會直接破壞快取。第三，使用 cached_prompt 或 cache_control 參數（OpenAI 支援）來明確標記哪些段落需要快取。以 OpenAI 為例，你可以在 messages 中加上 "cache_control": {"type": "ephemeral"}，這告訴 API「這段內容應該被快取，有效期約 5-10 分鐘」。對於 Vibe Coding 來說，了解這些機制可以讓你更好地設計 Agent 的提示模板，從而降低 Token 成本。

🔧 當 Vibe 破裂時的診斷方法

當你在 Vibe Coding 中發現 Agent 成本異常升高或回應速度變慢，可能是快取未生效。診斷的第一步是檢查 API 回應中的快取命中資訊。以 OpenAI API 為例，回應標頭中會包含 x-ai-prompt-cache-hit-tokens 和 x-ai-prompt-cache-miss-tokens 兩個欄位，分別代表快取命中與未命中的 token 數。如果你看到命中數為零，說明快取未生效，可能的原因包括：1. 每次請求的 prefix 不同（例如 system prompt 中有動態內容）；2. 推理參數不一致（temperature、top_p 等被修改）；3. 使用的 model 不支援快取（例如 gpt-4o 而非 gpt-4o-2024-05-13）。修復方法是統一 prompt 模板、固定推理參數，並確保 model 名稱包含版本號。對於 Claude API，快取行為更自動，但同樣需要注意不要隨機化開頭內容。

📊 成本計算與優化策略

快取命中後的定價與原始定價有顯著差異。以 OpenAI gpt-4o-2024-05-13 為例，輸入 token 原始價格為 $2.50 / 1M tokens，快取命中後價格降至 $0.25 / 1M tokens，降低約 90%。Claude 3.5 Sonnet 的快取命中價格約為 $1.60 / 1M tokens（原始為 $3.00 / 1M）。對 Vibe Coding 專案而言，這代表將 5,000 tokens 的 system prompt 設計成可快取的，比設計成每次重新計費，每月可節省數百元。具體策略包括：將專案規範、程式碼風格指南、工具定義等靜態資訊統一放在 system prompt 前段；避免在每次對話中加入時間戳、會話 ID 等動態內容；使用相同 model 名稱與參數；定期檢視 API 費率明细，確認快取命中率。

🔬 深入解析
為什麼快取只命中 prefix 而不是整個上下文？

快取的設計基於一個重要的技術事實：LLM 的推理過程是增量式的。當模型處理一個序列時，前 N 個 token 的計算結果（例如 attention 權重、KV cache）可以被重複使用，而不需要重新計算。這就是為什麼快取只針對「prefix」而非整個上下文——因為 prefix 的計算結果是最 stable 且最可能被重複使用的部分。當你在 Vibe Coding 中設計 Agent 時，理解這個機制可以幫助你更有策略地組織上下文：把不變的資訊放在 prefix，把會變動的資訊放在 suffix。例如，系統提示（system prompt）是最適合快取的內容，因為它通常是靜態的；工具定義（tool definitions）也是好選擇；但對話歷史中的具體內容（如用戶的具體問題）會每次都不同，無法被快取。此外，快取的有效期限制（通常 5-10 分鐘）意味著它適合「短時間內的連續請求」，而不適合跨時間長度的重用。這也解釋了為什麼在多輪對話中，保持每次請求的 prefix 一致是提升快取命中率的關鍵。

以下示範如何在 OpenAI API 中使用 cache_control 參數來明確標記需要快取的內容：

$ node --eval " const OpenAI = require('openai'); const client = new OpenAI(); async function chatWithCache() { const response = await client.chat.completions.create({ model: 'gpt-4o-2024-05-13', messages: [ { role: 'system', content: '你是一名 Next.js 專家。', cache_control: { type: 'ephemeral' } }, { role: 'user', content: '幫我建立一個 TODO 頁面' } ] }); console.log('Cache hit tokens:', response.usage?.prompt_cache_hit_tokens); console.log('Cache miss tokens:', response.usage?.prompt_cache_miss_tokens); } chatWithCache(); " # 執行後查看回傳的 usage 欄位 # 第二次相同請求時，cache_hit_tokens 會大幅增加 # 因為 system prompt 已被快取
